# Where the hands-free Moneysoft-to-Xero poster should run: runtime, scheduling, secrets and access

Research date: 26 Sep 2026. **Method and its limits.** The session's web-search budget was already exhausted (200/200) before this task started and the egress proxy blocks dropbox.com, help.dropbox.com, developer.xero.com, learn.microsoft.com, healthchecks.io, cronitor.io, pushover.net, missiveapp.com, docs.parallels.com and docs.github.com. What *was* reachable and read in full: Anthropic's own product documentation (code.claude.com/docs: Routines, scheduled tasks, Remote Control, cloud environments, Claude Code on the web; support.claude.com: Cowork scheduled tasks, computer use, Dispatch, Cowork architecture), Apple's Daemons and Services guide (developer.apple.com), GitHub's documentation source (github/docs repo), Microsoft's PowerShell and Graph documentation source (MicrosoftDocs repos), the Dropbox Python SDK source and Dropbox's official webhook sample (dropbox/mdwebhook), the healthchecks.io documentation source (healthchecks/healthchecks repo), the cronitor-python and python-pushover READMEs, PyPI metadata, and the practice's own skills (`payroll-agent`, `browns-payroll-journal`, `xero-payroll-backfill`, `holiday-portal-deploy`), the earlier research notes 02-04 in this folder, and the `msx` code already in this repository. Claims are labelled **[doc]** (read in full from the vendor's page/source), **[practice-verified]** (from the practice's skills or repo), **[note 0x]** (from an earlier research note in this folder, which rests on search snippets), or **[knowledge]** (my prior knowledge; web silent; confidence low/medium).

## Summary

- **Run the poster as a launchd LaunchAgent on ONE designated, always-awake Mac** (the machine that also hosts the Parallels VM and the live Dropbox replica), as a deterministic Python job with no model in the loop. Everything it needs is already local: the Moneysoft `.pay/.pfi` files, the filed PDFs, the Keychain, `pdftotext`, and the Xero API over HTTPS. This is the option with the fewest moving parts, the strongest secret story, and zero change to the `payroll-agent` flow (which already runs on that Mac and already files the PDFs the poster consumes). The repo's `deploy/launchd/uk.co.digivolve.msx.plist` is this design.
- **Sleep is the one real failure mode of a laptop-hosted poster, and it is solvable**: Apple documents that `StartCalendarInterval` jobs missed during sleep run at wake and every other launchd job (including `StartInterval`) is simply skipped while asleep; so use a calendar trigger plus `caffeinate`/`pmset`, or - better - make the poster live on a desk-bound Mac mini so there is no lid and no battery. The practice already knows a sleeping Mac suspends the VM (`payroll-agent` SKILL.md).
- **Claude Cowork scheduled tasks cannot be the runtime for a local-file job**: Anthropic's help centre says scheduled tasks run remotely, "can't be tied to a folder on your computer", and a task that needs local files or apps "will only run locally", which requires the desktop app open and the Mac awake (computer-use and Dispatch articles). They remain fine as the *trigger and reporter* for the existing payroll-agent, not as an unattended file watcher.
- **Cloud runners (Claude Code Routines, GitHub Actions cron) can post to Xero but pay a tax on the two things a cloud box does not have: the Dropbox files and durable private state.** Both are obtainable - Dropbox `list_folder`/`continue` cursor polling with `files.metadata.read` + `files.content.read`, and a small state file - but Xero's *rotating* refresh token (every refresh invalidates the old one, 60-day unused expiry, 30-minute grace) means a cloud poster must own its **own** Xero consent and its own token store; it can never share the Mac's token. Routines' minimum interval is one hour, they run without permission prompts, their Default network allowlist does not include api.xero.com or dropboxapi.com (verified from inside this very environment), and "green" run status only means the session exited cleanly.
- **Windows Task Scheduler inside the Parallels guest buys nothing**: posting needs no Moneysoft UI, the guest is suspended whenever the Mac sleeps, Dropbox reaches it only through the `\\Mac\Home` share (with online-only-placeholder risk), and it adds Python-on-Windows, DPAPI and a second machine profile to maintain. Keep the guest for driving Moneysoft only.
- **Secrets**: macOS Keychain generic-password item written by the `security` CLI (already implemented in `xero_client.KeychainTokenStore`); DPAPI (`Export-Clixml`) if anything ever must live in the guest; GitHub *environment* secrets (48 KB, 100 per environment) or Anthropic cloud-environment **API credentials** (Pro/Max only; proxy-attached, key never enters the VM) for a cloud fallback. Never a token in Dropbox, never in a Routine environment variable (readable by anyone using the environment).
- **Observability**: a dead-man's switch (healthchecks.io `/start` … success or `/fail` per run, period 30 min + grace) plus the run report through the Missive API the practice already uses (`POST /v1/drafts` with `send: true`), with Microsoft Graph `sendMail` (Application `Mail.Send`, the practice's existing Entra app) as the channel-of-last-resort. Bright Manager has no API - the tick stays in the Chrome-driven payroll-agent.
- **Recommendation**: primary = launchd on the designated Mac (ideally a Mac mini that becomes "the payroll machine"), stdlib-only Python plus `pdftotext`/`pypdf`, Keychain, healthchecks + Missive. Fallback = a Claude Code Routine (or GitHub Actions cron) poster with its own Dropbox app, its own Xero consent, its own ledger, that is normally **disabled** and is switched on only when the Mac is out of action - never both live at once against the same orgs.

## Findings

### A. macOS launchd / cron on a staff Mac (option 1)

**1. Confidence: high** - launchd's documented sleep behaviour differs by trigger type. Apple: "If the system is turned off or asleep, cron jobs do not execute; they will not run until the next designated time occurs. If you schedule a launchd job by setting the `StartCalendarInterval` key and the computer is asleep when the job should have run, your job will run when the computer wakes up. However, if the machine is off when the job should have run, the job does not execute until the next designated time occurs. All other launchd jobs are skipped when the computer is turned off or asleep." **[doc]** Consequence: the repo's plist uses `StartInterval` 1800 - fine as a poll loop while awake, but intervals during sleep are dropped, not coalesced. A `StartCalendarInterval` list (e.g. every 30 min) gives catch-up on wake. Source: [Apple - Scheduling Timed Jobs](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html).

**2. Confidence: high** - The practice already runs the exact prerequisites on these Macs: `caffeinate -dimsu &` before an unattended run ("a sleeping Mac suspends the VM; a sleeping *display* is fine"), a machine profile (`pa_env.py`) that resolves the live Dropbox Moneysoft folder and refuses to guess, and Python 3 with `pypdf` installed via `python3 -m pip install --user pypdf`. **[practice-verified]** Sources: `payroll-agent/SKILL.md`, `payroll-agent/references/setup.md`, `payroll-agent/references/moneysoft-playbook.md`.

**3. Confidence: high** - The repo's poster is already shaped for this runtime: `bin/msx run` (stdlib `urllib` Xero client, PKCE, `KeychainTokenStore` via the `security` CLI, SQLite ledger on local disk "never on Dropbox: sync + SQLite = corruption", `sources.stable()` that refuses a PDF until it is non-empty, unchanged for a sample interval and older than `settle_seconds`, a conflicted-copy regex, a weekly Xero token keep-alive, `notify.heartbeat()` that appends `/fail` "healthchecks.io convention", and a Missive run report). The launchd template says "Runs `msx run` every 30 minutes on the ONE Mac designated as the poster … A run is idempotent". **[practice-verified]** Sources: `src/msx/runner.py`, `src/msx/state.py`, `src/msx/sources.py`, `src/msx/notify.py`, `src/msx/xero_client.py`, `deploy/launchd/uk.co.digivolve.msx.plist`, `config.example.json`.

**4. Confidence: medium** - Keychain and unattended LaunchAgents. A LaunchAgent (`gui/<uid>` domain) runs inside the user's login session and can read the login keychain while that keychain is unlocked; the item must be created by the same user, and the first read from a new binary path can raise an ACL prompt. If the Mac sits at the login window (auto-login off, or FileVault pre-boot) the agent does not run at all; if the keychain is set to lock after sleep/inactivity, `security find-generic-password` fails. **[knowledge]** The `KeychainTokenStore` stores the whole token JSON base64-encoded as one generic-password item, which keeps the rotated refresh token and the access token together (one atomic write). **[practice-verified]** Verify on the office Mac: auto-login on, "Require password after sleep" behaviour, keychain lock settings, and that `security` from launchd needs no GUI prompt. Sources: `src/msx/xero_client.py`; web silent on the launchd/keychain interaction (learn/apple support pages blocked).

**5. Confidence: high** - Two Macs racing. Xero's refresh token rotates on every use and the old one dies (30-minute grace) **[note 03, high]**, so two machines cannot share one token set even via a synced file; and SQLite over Dropbox corrupts. Therefore "two Macs both running the poster" is not a race to arbitrate, it is a configuration error: exactly one machine holds `~/.config/msx/config.json`, one holds the Keychain item, one runs the LaunchAgent. The Xero read-before-write duplicate guard (`GET ManualJournals?where=Date…` then narration/total compare) remains the last line of defence if a second machine is ever mis-configured, and the `pa_env.py` pattern ("never a silent default") is the right way to make the second Mac refuse to post. **[practice-verified]** Sources: `payroll-agent/SKILL.md`, `docs/research/03-xero-manual-journals-api-and-auth.md`, `src/msx/state.py`.

**6. Confidence: medium** - Dropbox on macOS is on Apple's File Provider, so a file can be an online-only placeholder that a `\\Mac\...` share or a naive `open()` will not read; the Moneysoft folder and the PDF folder must be pinned "available offline" on the poster Mac. **[note 02, medium]** The repo already holds a PDF (`sources.is_pdf`) until it is readable and reports "online-only Dropbox placeholder? re-download it". **[practice-verified]** Sources: [Dropbox online-only files on macOS](https://help.dropbox.com/sync/online-only-mac) (via note 02), `src/msx/runner.py`.

### B. Windows Task Scheduler inside the Parallels guest (option 2)

**7. Confidence: high** - The guest can see the Mac's files through Parallels shared folders: the Save dialog in Moneysoft defaults to `C:\Mac\Home\Documents` (= `~/Documents` on the Mac) and the practice shares `~/PayrollShared` into Windows as `\\Mac\PayrollShared`. **[practice-verified]** So the Dropbox PDF folder is reachable from the guest as `\\Mac\Home\Library\CloudStorage\Dropbox-…` only if the Mac home folder sharing is on - and an online-only placeholder read through that share is a documented failure mode to rule out **[note 02]**. Sources: `payroll-agent/references/moneysoft-playbook.md`, `payroll-agent/references/setup.md`, note 02 finding 10.

**8. Confidence: high** - The guest exists only while the Mac is awake: "a sleeping Mac suspends the VM". **[practice-verified]** Task Scheduler's "wake the computer to run this task" wakes Windows, not the Mac hosting it. So option 2 inherits every sleep problem of option 1 and adds the VM as a second thing that must be running. Sources: `payroll-agent/SKILL.md`.

**9. Confidence: high** - Task Scheduler interactive vs non-interactive. The practice's Moneysoft driver must be an interactive task (`schtasks /IT /RU <guest_user>`, user logged on) because `prlctl exec` alone "is SYSTEM in session 0 and can neither see windows nor send keys". **[practice-verified]** A *poster* needs no window, so it could run as "Run whether user is logged on or not" (stored password or S4U) **[knowledge]** - but that only matters if you choose to put the poster in the guest, which finding 8 argues against. Sources: `payroll-agent/SKILL.md`; note 02 finding on `prlctl`/`schtasks`.

**10. Confidence: high** - Secrets in the guest: PowerShell `Export-Clixml` "encrypts credential objects by using the Windows Data Protection API. The encryption ensures that only your user account on only that computer can decrypt the contents of the credential object. The exported CLIXML file can't be used on a different computer or by a different user." **[doc]** That is adequate for a refresh token, but it ties the token to one Windows user on one VM image - a VM restore from a snapshot silently reverts the rotated Xero refresh token to a dead one. Source: [Export-Clixml (PowerShell docs source)](https://github.com/MicrosoftDocs/PowerShell-Docs/blob/main/reference/7.4/Microsoft.PowerShell.Utility/Export-Clixml.md).

**11. Confidence: medium** - Python is not present in a stock Windows guest; the practice's guest tooling is pure PowerShell (`pa_*` scripts) **[practice-verified]**, so a Python poster there means a new install to maintain, a second copy of the repo, and a second machine profile. Nothing about posting benefits from being "closer to Moneysoft" - the poster reads PDFs that `split_reports.py` has already written on the Mac side. Sources: `payroll-agent/SKILL.md` (guest task table), `payroll-agent/references/setup.md`.

### D. Claude Code Routines and GitHub Actions cron (option 4)

**17. Confidence: high** - Routines: "Routines execute on Anthropic-managed cloud infrastructure … so they keep working when your laptop is closed"; triggers are Scheduled, API (POST with a per-routine bearer token, `text` arrives wrapped as untrusted data) and GitHub events; "The minimum interval is one hour; expressions that run more frequently are rejected"; "If you schedule a run exactly on the hour … it can start several minutes late"; "Routines run autonomously as full Claude Code cloud sessions: there is no permission-mode picker, and the session runs shell commands … and calls any connectors you include, all without stopping for approval"; "Routines belong to your individual claude.ai account … and they count against your account's daily run allowance"; "A green status in the run list means the session started and exited without an infrastructure error. It does not mean the task in your prompt succeeded." Routines "are in research preview". They need GitHub access to clone the repo and pause after 72 h without it. **[doc]** Source: [Automate work with routines](https://code.claude.com/docs/en/routines).

**18. Confidence: high** - Cloud environment secrets and network. "Environment variables … Anyone who uses the environment can read the values." "An API credential is an API key or token you store on a cloud environment so Claude can call that API from any session in the environment without seeing the key. Anthropic's agent proxy adds the key to requests for the hosts you list … The key never reaches Claude, the commands it runs, or the session's environment variables." "API credentials are available on Pro and Max plans. They aren't available on Team or Enterprise plans yet." Network levels: None / Trusted ("package registries, GitHub, cloud SDKs") / Custom / Full; hosts outside the allowlist "fail with 403 and x-deny-reason: host_not_allowed"; connector traffic bypasses the allowlist; the setup-script cache expires "after roughly seven days"; idle sessions are reclaimed. **[doc]** Verified from inside this session's Default environment: `identity.xero.com`, `api.dropboxapi.com`, `healthchecks.io`, `missiveapp.com` are all refused (`CONNECT tunnel failed, response 403`), while `raw.githubusercontent.com`, `api.github.com`, `pypi.org`, `developer.apple.com`, `code.claude.com` succeed - so a Routine poster needs a Custom allowlist (`api.xero.com`, `identity.xero.com`, `api.dropboxapi.com`, `content.dropboxapi.com`, `notify.dropboxapi.com`, `public.missiveapp.com`, `hc-ping.com`). Sources: [Cloud environments](https://code.claude.com/docs/en/cloud-environments), [Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web), this session's `list_environments` result (one environment, "Default", `anthropic_cloud`).

**19. Confidence: high (design-critical)** - A cloud poster cannot borrow the Mac's Xero token. Xero: "every refresh returns a new refresh token and invalidates the old one", unused refresh tokens expire after 60 days, retry grace 30 minutes **[note 03, high, from developer.xero.com snippets]**. A Routine has no writable durable config (it cannot update its own environment variables), and an API credential is a *static* header value - it cannot express an OAuth refresh dance. So a Routine poster must (a) hold its own Xero consent (separate PKCE app or a separate authorising user), and (b) persist the rotated refresh token itself somewhere it can read next run: a private GitHub repo file written back with the session's GitHub identity (Routines act "as you: commits and pull requests carry your GitHub user"), a Dropbox app-folder file, or the Artifact database. Each is a new secret-at-rest. GitHub Actions has the same problem; a workflow can only rewrite a secret via the API with a PAT that is itself a secret **[knowledge, medium]**. Dropbox refresh tokens, by contrast, are long-lived and not rotated on use **[knowledge, medium]**, so Dropbox is easy to hold in a static secret. Sources: note 03 findings 16, 19; [Routines](https://code.claude.com/docs/en/routines); [Cloud environments](https://code.claude.com/docs/en/cloud-environments).

**20. Confidence: high** - GitHub Actions `schedule`: "The shortest interval you can run scheduled workflows is once every 5 minutes"; runs in UTC unless a `timezone` is set; "The `schedule` event can be delayed during periods of high loads … High load times include the start of every hour. If the load is sufficiently high enough, some queued jobs may be dropped."; "Scheduled workflows will only run on the default branch"; "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days" (private repos are not subject to this). Secrets: "Secrets are limited to 48 KB", 100 repository and 100 environment secrets; environment secrets can sit behind required reviewers. Billing: minutes for private repos come from the plan's quota; usage on self-hosted runners is free. **[doc]** Sources: [events-that-trigger-workflows (github/docs)](https://github.com/github/docs/blob/main/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md), [reusable schedule-delay](https://github.com/github/docs/blob/main/data/reusables/actions/schedule-delay.md), [secrets reference](https://github.com/github/docs/blob/main/content/actions/reference/security/secrets.md), [Actions billing](https://github.com/github/docs/blob/main/content/billing/concepts/product-billing/github-actions.md).

**21. Confidence: medium** - Hybrid worth knowing about: a GitHub Actions **self-hosted runner** installed on the designated Mac (`./svc.sh install` registers it as a launchd service) turns GitHub cron into a trigger for a job that executes *on the Mac* with the Dropbox files local, with secrets injected from GitHub and logs kept in GitHub. **[doc for the service install; knowledge for the rest]** It is neat but adds a permanently-connected agent with repo-scoped credentials on a machine holding payroll data; GitHub warns against self-hosted runners with public repos. It does not fix sleep. Not recommended over plain launchd, but it is the cheapest path if the practice wants GitHub as the control plane. Source: [Configure the self-hosted runner application as a service](https://github.com/github/docs/blob/main/content/actions/how-tos/manage-runners/self-hosted-runners/configure-the-application.md).

**22. Confidence: medium** - Cost/usage: "There is no separate compute charge for the cloud VM" and cloud sessions "share rate limits with all other Claude and Claude Code usage within your account" **[doc]**; a Routine run consumes model tokens even when the job is deterministic and there is nothing to do, and counts against a daily run allowance. GitHub Actions on a private repo consumes plan minutes (Free plan 2,000 min/month **[knowledge, medium]**); a 1-minute poll every 30 minutes is ~1,500 min/month, i.e. it eats most of a free allowance - poll hourly or on a Dropbox webhook instead. Sources: [Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web); [Actions billing](https://github.com/github/docs/blob/main/content/billing/concepts/product-billing/github-actions.md).

### E. Dropbox API for a cloud watcher (option 5)

**23. Confidence: high** - Change detection is cursor-based. `files/list_folder` (scope `files.metadata.read`) returns entries and a cursor; "If the result's `has_more` field is true, call `files_list_folder_continue` with the returned cursor"; `list_folder/continue` "retrieve[s] updates to the folder"; `list_folder/get_latest_cursor` gives a starting cursor without listing; `recursive=True` "may lead to performance issues or errors … with a large number of items". `list_folder/longpoll` (no auth, notify host) "will block until there are changes available or a timeout occurs … timeout in seconds … plus up to 90 seconds of random jitter"; the result has `changes` and an optional `backoff` ("backoff for at least this many seconds before calling"). "`auth.RateLimitError` may be returned if multiple `files_list_folder` or `files_list_folder_continue` calls with same parameters are made simultaneously". Download is `files/download` (scope `files.content.read`), `files_download_to_file` in the SDK. **[doc - SDK source]** Sources: [dropbox/base.py](https://github.com/dropbox/dropbox-sdk-python/blob/main/dropbox/base.py), [dropbox/files.py](https://github.com/dropbox/dropbox-sdk-python/blob/main/dropbox/files.py).

**24. Confidence: high** - Webhooks tell you *who* changed, not *what*. Dropbox's official sample verifies a GET `challenge` echo and, on POST, checks `X-Dropbox-Signature` = HMAC-SHA256(app secret, raw body) with `hmac.compare_digest`, then iterates `json['list_folder']['accounts']` and runs `list_folder`/`list_folder_continue` from the stored cursor per account - "We need to respond quickly to the webhook request, so we do the actual work in a separate thread". **[doc - official sample]** A webhook therefore needs a public HTTPS endpoint and the app secret; for a practice with no server, cursor polling (or a Routine/Actions cron that calls `list_folder/continue`) is simpler and has no inbound surface. Source: [dropbox/mdwebhook app.py](https://github.com/dropbox/mdwebhook/blob/master/app.py), [README](https://github.com/dropbox/mdwebhook/blob/master/README.md).

**25. Confidence: high** - OAuth for a script. The SDK's OAuth flow takes `token_access_type` in `["offline", "online", "legacy"]` and `use_pkce`; "Must pass in either consumer secret or use PKCE"; the `Dropbox` client takes `oauth2_refresh_token` + `app_key` (+ `app_secret`, "Not required if PKCE was used to authorize the token") and `check_and_refresh_access_token()` refreshes before expiry. Rate limiting: `max_retries_on_rate_limit` "On 429 errors, the number of times to retry. If `None`, always retries." The SDK depends on `requests` and `stone` (PyPI metadata), so a stdlib-only poster would call the HTTP endpoints directly (`/2/files/list_folder`, `/continue`, `/download`, `/oauth2/token` with `grant_type=refresh_token`). **[doc - SDK source, PyPI]** Sources: [dropbox/oauth.py](https://github.com/dropbox/dropbox-sdk-python/blob/main/dropbox/oauth.py), [dropbox/dropbox_client.py](https://github.com/dropbox/dropbox-sdk-python/blob/main/dropbox/dropbox_client.py), [PyPI dropbox 12.2.2](https://pypi.org/pypi/dropbox/json).

**26. Confidence: medium (design-critical for option 4/5)** - App folder vs full Dropbox. Dropbox's sample recommends "App folder" permission ("My app only needs access to files it creates") **[doc]**. The practice's PDFs are written by `split_reports.py` into an existing team folder (`Dropbox - Moneysoft Backups/PDF attachments`), not into an app folder, so an app-folder-scoped app cannot see them **[knowledge, medium - the app-folder sandbox is `/Apps/<name>` only]**. Either the poster app is granted **full Dropbox** access (larger blast radius: every file the authorising user can see, including the `.pay` files) or `split_reports.py` is changed to also copy each filed PDF into `/Apps/<poster>/inbox/<client>/…`, which keeps the cloud poster app-folder-scoped and gives the watcher a clean, small folder to cursor over. The second is the safer design. Sources: [dropbox/mdwebhook README](https://github.com/dropbox/mdwebhook/blob/master/README.md), `payroll-agent/references/moneysoft-playbook.md`, `config.example.json`.

**27. Confidence: medium** - Dropbox rate limits: the API returns HTTP 429 with a `Retry-After`/`retry_after` value and the SDK retries indefinitely by default (finding 25); published per-app numbers are not documented on the pages reachable here **[knowledge: limits are per app per user and generous for a folder polled every 30 minutes; low]**. One `list_folder/continue` per poll and one download per new PDF is trivially inside any limit. Source: [dropbox_client.py](https://github.com/dropbox/dropbox-sdk-python/blob/main/dropbox/dropbox_client.py).

**28. Confidence: medium** - Team accounts: if the Dropbox folder is a team folder, the token must be for a member with access and, on Business accounts, requests may need the `Dropbox-API-Path-Root` header (`PathRoot` in the SDK) to see team-space paths **[knowledge; the SDK exposes `with_path_root(PathRoot)`]**. Verify on the office machine whether "Dropbox - Moneysoft Backups" is a personal shared folder or a team folder. Source: [dropbox_client.py](https://github.com/dropbox/dropbox-sdk-python/blob/main/dropbox/dropbox_client.py).

## Implications for the pipeline design

1. **Designate one poster machine and make the others refuse.** `config.json` gets `poster: true` on exactly one Mac; `msx run` on any other machine exits with "this machine is not the designated poster" (the `pa_env.py` "never a silent default" pattern). The ledger and Keychain item exist only there. The Xero read-before-write duplicate guard stays as the backstop.
2. **Trigger with `StartCalendarInterval` (every 30 min, 06:00-22:00) rather than `StartInterval`,** so runs missed during sleep coalesce into one at wake (finding 1). Keep `RunAtLoad`. On a laptop, pair with a `pmset repeat wake` schedule or `caffeinate` inside the run; on a Mac mini set Energy Saver to never sleep and "Start up automatically after a power failure".
3. **Split the poster into two phases with separate healthchecks:** (a) `discover+build+reconcile` (pure local, no secrets) and (b) `post` (Keychain + Xero). Ping `/start` at the top, `/` on success, `/fail` (with the HOLDS summary as the POST body, `/log` is also available) on any hold; period 30 min, grace 20 min for the poster; a second daily check for the Xero keep-alive refresh.
4. **Keychain hygiene:** one generic-password item per Xero app, written atomically after every refresh (already done), plus a `msx auth status` that alerts when `refresh_token_expires_at < 7 days` or a refresh returns `invalid_grant`. Confirm auto-login + keychain-unlock behaviour on the poster Mac (open question 1).
5. **Do not put the poster in the Windows guest** (findings 7-11). The guest's job remains: drive Moneysoft, export the combined PDF into `C:\Mac\Home\…`, and let `split_reports.py` file it. The guest never sees the Xero token.
6. **Cowork/Desktop scheduled tasks stay as the orchestration layer**: `payroll-agent-sweep` runs payroll and files PDFs; after posting, a Cowork task reads `HOLDS.md`/the ledger, ticks Bright Manager in Chrome (no API), and writes the shift-log line Kate AI reads. None of them decides whether a journal posts.
7. **Build the cloud fallback now, but keep it off.** (a) Make `split_reports.py` also drop each filed PDF into a Dropbox **app folder** (`/Apps/msx-poster/inbox/<client>/…`) so the fallback's Dropbox app can be app-folder-scoped; (b) add a `sources.dropbox_api` backend that walks `list_folder`/`continue` from a stored cursor, downloads new PDFs to a temp dir, and feeds the same parser; (c) give the fallback its **own** Xero PKCE consent (finding 19) and a token store it can persist (a private-repo file committed by the run, or an app-folder file), never the Mac's; (d) its ledger is separate, so the Xero read-before-write guard is what prevents a double post if both were ever on together - make the fallback default to `draft` mode for that reason; (e) Custom network allowlist listing the Xero/Dropbox/Missive/healthchecks hosts (finding 18); (f) hourly schedule at :07, since Routines cannot run more often and on-the-hour starts are late.
8. **Alerting order:** healthchecks (missing/failed/hung run) → Missive run report to Matt (`send: true`) + internal note on holds → Graph `sendMail` from `payroll@digivolve.co.uk` if the Missive call fails (already "failure to notify never fails the run"). No Bright Manager writes from the poster.
9. **Packaging:** stdlib + `pdftotext` (poppler) with `pypdf` fallback; pin `/opt/homebrew/bin/python3` in the plist; `bin/msx doctor` should check python version, `pdftotext`/`pypdf`, Keychain access, Dropbox folder pinned offline, `settle_seconds`, healthchecks URL reachable, and print PASS/FAIL lines a Cowork task can read.
10. **Idempotency across runtimes**: the narration key (`Payroll - <Mon YYYY> (Mn)`) plus period-window `GET ManualJournals` must stay the cross-runtime duplicate guard, because the Mac's SQLite ledger and a fallback's ledger will never see each other (note 03 says Xero's `Idempotency-Key` protects retries within ~24 h only).
