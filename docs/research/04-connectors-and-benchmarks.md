# Moneysoft-to-Xero connectors and how best-in-class payroll products post journals to Xero

Research note for the Digivolve hands-free payroll-journal pipeline. Written 26 Sep 2026.

**Method and its limits.** The session's web-search budget was already exhausted and the egress proxy blocks developer.xero.com, central.xero.com, moneysoft.co.uk, brightpay.co.uk and api.staffology.co.uk. What *was* reachable: GitHub code search (fragments) and raw.githubusercontent.com (full files). So every claim below rests on one of: (a) public source code / API specifications on GitHub (Xero's own OpenAPI spec, Staffology's OpenAPI spec, Employment Hero/KeyPay's generated .NET client), (b) mirrored copies of Xero Central / Xero developer pages, (c) a public repo containing real BrightPay-generated Xero journals, (d) a public repo of a UK accountancy practice (Almond Valley Accounting) that automated BrightPay journal posting at ~100-employer scale, or (e) the practice's own skills. Where the web was silent (Moneysoft's own export features, AccountingWEB/ICB forum sentiment, BrightPay's setup UI) I say so and give a best-knowledge answer at low/medium confidence. Every fact needing a look at the office machine is listed at the end.

## Summary

- **No Moneysoft-to-Xero connector exists anywhere findable.** Zero GitHub repos or code for "moneysoft" + "xero"/"payroll manager" journals, no Zapier/Make recipes surfaced, and HMRC's own software list records Moneysoft's "accounting" capability as its *own* Money Manager product. The practice's parse-the-Employer's-Summary approach is the only route, and it is the right one; nobody has a shortcut to copy.
- **Every serious UK payroll product posts to Xero via the ManualJournals API, dated on the pay date, status POSTED (not draft), with a nominal code per pay element and a source marker in the narration** (BrightPay: `Sent from BrightPay`; Staffology: `date = PaymentDate from the PayRun`, `autoSubmitJournal` on finalise; KeyPay: `ExportJournals` on finalise). Xero's old developer guide recommending an Accounts Payable bill instead is 2016-era and ignored by the whole market.
- **Employment Allowance is opt-in and silently droppable in all three benchmark products.** Staffology has `includeEmploymentAllowanceOnMonthlyJournal`, KeyPay has `IncludeEmploymentAllowanceInJournals`, and BrightPay posts EA as a *separate* journal that is skipped when no nominal is mapped (Almond Valley found £2,030 and £1,743 of EA unposted in July 2026 for exactly that reason; a 2021 Xero org shows a bookkeeper hand-posting `NIC Allowance - Month n` every month to fix the same gap). Digivolve's explicit Dr PAYE / Cr ER-NIC pair and P30 tie-out is *better* than the benchmarks, not a workaround.
- **Design-critical Xero constraint: an uncertified Xero OAuth app can connect to at most 25 organisations.** With ~260 employers the API route needs either Xero app certification (App Partner programme) or per-org Custom Connections (one org each, machine-to-machine). Rate limits (60/min, 5,000/day per tenant) are irrelevant at one journal per employer per month, but the 25-org cap decides the architecture.
- **Xero gives no idempotency key on ManualJournals.** Duplicate prevention is the caller's job everywhere: Staffology refuses to re-post without `force=true`, KeyPay returns `FailureAlreadyExported`, and the Almond Valley control check flags "same date + same total" as a duplicate. Re-posting after a payroll re-run never auto-reverses; the old journal is voided by hand (visible as POSTED/VOIDED pairs on the same pay date in the BrightPay data).
- **The peer practice's lesson: native posting was not hands-free at bureau scale.** Almond Valley drove BrightPay's own journal wizard with Playwright across ~99 employers and still built an independent ledger-side reconciliation (duplicates, missing, amount mismatch, orphans, uncategorised accounts, EA-not-mapped). Switching Digivolve's 260 employers to BrightPay/Staffology/Xero Payroll buys a nominal-mapping UI and an API, not the absence of a control layer.
- **Recommended shape (detailed in the implications section):** keep Moneysoft, keep the parser-plus-reconciliation core, replace the Chrome-driven CSV import with a Xero API poster that (1) checks for an existing journal by narration key and date before posting, (2) posts POSTED with a deterministic narration key, (3) records the ManualJournalID against the run, and (4) runs a separate read-only recon sweep after each batch. Decide the 25-org problem first.

## Findings

### 1. No third-party Moneysoft Payroll Manager to Xero connector exists (or is findable)

**Confidence: high** (for GitHub / open source), **medium** (for commercial connectors, because vendor sites were unreachable)

- GitHub repository search for `moneysoft payroll`, `moneysoft xero`, `payroll manager moneysoft` returned no repositories at all; code search returned only job adverts ("RTI Payroll for approximately 100 payroll clients ... on Moneysoft"), domain lists and marketing pages. No parser, journal builder or Xero poster for Moneysoft output exists in public code.
- HMRC's software-choices service source lists Moneysoft with `"business": true, "agent": true, "accounting": true` pointing at `moneysoft.co.uk/business-edition/` - i.e. the "accounting" capability HMRC records for Moneysoft is its own Money Manager bookkeeping product, not an integration to third-party ledgers. Source: [hmrc/software-choices-frontend conf/SoftwareProviders.json](https://github.com/hmrc/software-choices-frontend/blob/main/conf/SoftwareProviders.json).
- Staffology's list of accounting integrations (`ExternalDataProviderId` enum: Xero, Qbo, Sage, KashFlow, FreeAgent, Twinfield, AccountsIQ, NetSuite...) and KeyPay's `JournalService` string both show what a "connector" looks like in this market: it is built into the payroll product. Nothing consumes Moneysoft files. Source: [SynergiTech/staffology-swagger swagger.json](https://github.com/SynergiTech/staffology-swagger).
- Zapier/Make/Power Automate: no findable recipe. Moneysoft is a Windows desktop app with no API, so there is nothing for those platforms to trigger on except a file appearing in Dropbox - which is precisely the practice's existing "watch the PDF attachments folder" pattern.
- *Best-knowledge, low confidence (web silent):* Moneysoft Payroll Manager's built-in accounting output is a nominal-ledger analysis report and an export intended for Moneysoft's Money Manager; there is no Xero-format export. This must be verified on the office machine (see open questions) because a native CSV of pay-element totals per employee would be a far better parser input than `pdftotext -layout` on the Employer's Summary.

### 2. What BrightPay actually posts to Xero (from real journal data)

**Confidence: high** for the journal shape (observed data); **medium** for the setup UI (from memory; BrightPay docs unreachable)

A public repository contains a Xero org's full ManualJournals export in which BrightPay posted 31 fortnightly payroll journals between Jul 2021 and Jun 2022. Source: [maddy-codes/FinalAppRevComp Main/pythonCollection/xero_output_journals.txt](https://github.com/maddy-codes/FinalAppRevComp/blob/main/Main/pythonCollection/xero_output_journals.txt) and [journal_new.csv](https://github.com/maddy-codes/FinalAppRevComp/blob/main/Main/pythonCollection/journal_new.csv). What it shows:

- **One journal per pay run, dated the pay date** (fortnightly dates 02-Jul, 16-Jul, 30-Jul ...), not the period end and not month end.
- **Status `POSTED`, `LineAmountTypes: NoTax`, `TaxType: NONE`, `ShowOnCashBasisReports: true`.** BrightPay does not create drafts.
- **Narration is the fixed string `Sent from BrightPay`** on every journal - no period, no pay date, no employer. Per-line `Description` is the employee name only.
- **Four lines per employee, no merging:** Dr gross to 7003, Dr employer NIC to 7006, **Cr PAYE/NIC liability to 2210 as one line per employee** (tax + EE NIC + ER NIC combined: 343.60 on 1,160 gross), Cr net pay to 2220. This is the "eleven PAYE lines instead of one" that Digivolve saw on Browns Garage journal #109278 - it is BrightPay's normal shape, not a misconfiguration.
- **Employment Allowance was not posted by BrightPay in that org.** The bookkeeper posted a separate manual journal `NIC Allowance - Month n` (Dr 2210 / Cr 7006, 226.32) at each month end for twelve months, and a `Duplicate wages & PAYE write-off` journal. That is the same symptom Digivolve found (PAYE credited with full employer NIC, allowance never reversed).
- **Re-sends leave POSTED + VOIDED pairs on the same pay date** (02-Jul-2021, 11-Mar, 25-Mar, 08-Apr, 22-Apr-2022). A re-run in BrightPay followed by re-sending created a second journal; someone then voided the first in Xero. BrightPay does not reverse or update the earlier journal.

The 2026 behaviour, verified by a peer practice against live QuickBooks (BrightPay's QBO path, which shares the journal engine): "BrightPay posts the payroll journal and the Employment Allowance adjustment as SEPARATE journals ... Verified: MAC Recruit July = 31,845.98 + 3,331.24"; "Every one carries PrivateNote = 'Sent from BrightPay'"; "DocNumber is null. There is no per-period reference to match on"; "TxnDate is the period end, and it is not always month-end (May 2026 posted as the 29th)"; and two employers had `ea_status='not_mapped'` - "the journal posted, the Employment Allowance did not" (LA Travel £2,030.27; Local Planet Solutions £1,743.47). One employer failed outright with "no saved nominal ledger mapping". Source: [almondvalleyaccounting/athena-portal supabase/functions/qbo-journal-recon/index.ts](https://github.com/almondvalleyaccounting/athena-portal/blob/main/supabase/functions/qbo-journal-recon/index.ts) and [docs/qbo-portfolio-sweep-plan.md](https://github.com/almondvalleyaccounting/athena-portal/blob/main/docs/qbo-portfolio-sweep-plan.md).

*Best-knowledge on the BrightPay UI (medium confidence):* per employer file, Journals > Xero > connect (OAuth per employer), then a nominal mapping grid per pay item / addition / deduction / employer cost / liability with the Xero chart pulled live; options for merging lines per nominal, date choice, and inclusion of the Employment Allowance line - the EA line requiring its own nominal mapping is consistent with the "not_mapped" state above. Verify against a BrightPay file if one is still installed.

### 3. Staffology (IRIS) - the most explicit bureau-grade journal model

**Confidence: high** (read directly from Staffology's OpenAPI specification)

Source: [SynergiTech/staffology-swagger swagger.json](https://github.com/SynergiTech/staffology-swagger) (mirror of `api.staffology.co.uk/swagger/v1/swagger.json`, which is blocked here).

- **Mapping model:** `NominalCodeMapping { payCode, nominalCode, nominalName, nominalMapping, externalId }` - one row per pay code (pay element), employer-wide. `externalId` is "the Id of the nominal code in the external system ... If there's no mapping then this will have a value of '0'". Employer setting `nominalMappingsEnabled` "Enables the nominal mappings (Custom Codes, System Codes, Control Codes, Employer Codes)".
- **Overrides are by department and cost centre, not by employee:** `departmentJournalOverridesEnabled`, `costCentreJournalOverridesEnabled`, endpoints `/journaltokens/{departmentId}/departmentjournaloverrides`. `PayRunSummaryLine` carries `departmentCode`, `costCentreCode`, `analysisCategoryCodes` "if the journal is split by department / cost centre / analysis categories". GET journal takes `deptBreakdown=true` "and the journal will be split between any relevant Departments".
- **Pensions:** `PensionSchemeNominalCodeMapping { payCode, nominalCode, nominalName, journalNarrative }` - pension pay codes map per scheme, with their own narrative.
- **Merge vs detail:** employer setting `mergeMatchingNominalsEnabled`; `PayRunJournal.mergeMatchingNominals` echoes it per posted journal.
- **Date:** `PayRunJournal.date` = "The PaymentDate from the PayRun". Pay date, not period end.
- **Employment Allowance:** `HmrcDetails.includeEmploymentAllowanceOnMonthlyJournal` - "If the employer is not on a QuarterlyPaymentSchedule and is claiming EmploymentAllowance, then set this to true to include a line for Employment Allowance on the journal for the monthly schedule." Default is off. Quarterly payers get no EA line on the journal at all.
- **Automation:** `AutomationSettings.autoSubmitJournal` - "we'll automatically submit the payroll journal whenever you finalise a PayRun. The employer must be connected to an ExternalDataProvider supporting Type of 'Accounting'." Sits beside `autoSubmitFps`, `autoSubmitEps`, `autoSubmitPayslips`, `autoSubmitPayments`, `enableAutoPilot` - the product's "hands-free" is finalise-triggered fan-out.
- **Duplicate prevention and re-posting:** `POST /employers/{id}/external-data/{provider}/{taxYear}/{payPeriod}/{periodNumber}/journal` has `force` - "Set to true if you want to force the journal to be posted even if it already has been". The response warns "A 200 response does not mean the journal was necessarily successfully posted ... inspect the status". `PayRunJournal` records `status`, `statusMessage`, `link` ("a link to the journal in the ExternalDataProvider"). A user preference `allowJournalResubmit` gates re-sends in the UI.
- **Journal token/template system:** `JournalTokenType {SystemToken, CustomToken, TextToken, ValueToken}` and a per-employer `JournalTemplate` (header + content, CSV) - the CSV export is fully templatable, which is how bureaux feed non-integrated ledgers.

### 4. Employment Hero / KeyPay - the same decisions, expressed as a chart-of-accounts object

**Confidence: high** (read from the vendor's generated .NET client)

Source: [Thinkei/keypay-dotnet-v2](https://github.com/Thinkei/keypay-dotnet-v2), files under `src/keypay-dotnet/Uk/`.

- **Mapping model:** `UkChartOfAccountsDefaultAccountsModel` holds one account id per journal item type - `PayeLiabilityAccountId`, `PayeExpenseAccountId`, `NationalInsuranceLiabilityAccountId`, `NationalInsuranceExpenseAccountId`, `EmployeeNationalInsuranceLiabilityAccountId`, `EmployerPensionLiability/ExpenseAccountId`, `EmployeePensionLiabilityAccountId`, `StudentLoanLiabilityAccountId`, `PaymentAccountId` (net pay), `DefaultExpenseAccountId` - plus per pay category (`ChartOfAccountsCategoryModel { Name, ExpenseAccountId }`) and per deduction / employer-liability category.
- **Overrides are per location and per employing entity**, via `...SplitByLocation` / `...SplitByEmployingEntity` booleans on every account and `LocationSpecificChartOfAccounts`. Again: no per-employee mapping. Directors' pay to a DLA would be modelled as a separate pay category with its own expense account.
- **Summary vs detail:** `JournalView { Summary, Details, Both, Excel }`; `UkJournalItemResponse` carries `Reference`, `Details`, `Location`, `TaxCode`, `IsDebit/IsCredit`, `Amount` and `AmountUnrounded`.
- **Trigger and timing:** `FinalisePayRunOptions { DatePaid, ExportJournals, ExportJournalsPreference {Manual, Immediate, Scheduled}, ExportJournalsDateTime, LodgePayRun (FPS) ... }` and `PayRunFinaliseDefaultSettingsModel { ExportJournalsTimeline {Before, After, On}, ExportJournalsDay, ExportJournalsTimeOfDay }`. Journal export is an action of finalising the pay run, schedulable relative to the pay date.
- **Employment Allowance:** `UkEmploymentAllowanceModel.IncludeEmploymentAllowanceInJournals` (boolean, alongside `EmpAllowanceClaimedInAnotherPayrollProductThisTaxYear`).
- **Failure taxonomy worth copying:** `JournalExportStatus { NotExported, Success, FailureAccountsNotConfigured, FailureAccountPeriodClosed, FailureNotAuthenticated, FailureAlreadyExported, FailureCannotUseAccountsPayableAccount, FailureVendorMessage, FailureAPIError, FailureMissingTaxInfo, FailureRecordingJournalReference, FailureNoJournalId, FailuresTenantNotSupplied ... }` and `JournalExportResult { Status, Message, JournalSource, JournalExternalReferenceId }`. Note especially `FailureRecordingJournalReference`: the vendor treats "posted to the ledger but failed to record the ledger's id locally" as its own failure class.

### 5. Xero's own guidance and the ManualJournals contract

**Confidence: high** for the API contract and Central articles; **medium** that the mirrored developer guide reflects Xero's *current* wording (the mirror is from ~2016; the live page was unreachable)

- The mirrored Xero developer guide "Integrate a Payroll system" says: "Our recommended approach for handling payroll integration with Xero is to use Accounts Payable invoices ... We have tried to reduce the need for anyone to create general journals in Xero. General journals in Xero cannot be posted to a bank account and a collection of system accounts (e.g. Accounts Payable)." The worked UK example is wages £2,500 + NI £259.07, a bill whose lines are the debits (positive) and credits (negative) with net pay as the bill total, paid from the bank or from a "Salaries Liability" clearing account with "Enable payments to this account" ticked. Source: [coderbec/xero-dash-docset api-guides/how-to-integrate-my-payroll-system-with-xero](https://github.com/coderbec/xero-dash-docset/blob/master/api-guides/how-to-integrate-my-payroll-system-with-xero/index.html) (mirror of developer.xero.com/documentation/api-guides/how-to-integrate-my-payroll-system-with-xero/). The market ignored this: BrightPay, Staffology and KeyPay all use ManualJournals (finding 2-4). The bill approach's only real advantage - net pay reconciles as a bill payment - is lost for a bureau whose clients pay staff from many bank feeds anyway.
- **ManualJournal schema** (Xero's published OpenAPI): `Narration` (required), `Date` "YYYY-MM-DD", `Status` enum `DRAFT | POSTED | DELETED | VOIDED | ARCHIVED`, `LineAmountTypes`, `ShowOnCashBasisReports` (default true), `Url` ("Url link to a source document - shown as 'Go to [appName]' in the Xero app"), `JournalLines[] { LineAmount (debits positive, credits negative), AccountCode | AccountID, Description, TaxType, Tracking[] (max 2) }`. Warnings such as "Account code '476' has been removed as it does not match a recognised account" come back in the response. There is no idempotency or external-reference field beyond `Narration` and `Url`. Source: [XeroAPI/Xero-OpenAPI xero_accounting.yaml](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml).
- **System accounts that refuse manual journals:** Accounts Payable, Accounts Receivable, Bank Revaluation, Current Earnings, Tracking Transfers, Unpaid Expense Claims, Unrealised Currency Gains and **Wage Payables** (Xero Payroll's own liability account) all "No". So a pipeline must credit net pay to an ordinary liability code (the practice's 814 / 2200 / 2220 conventions), never to Xero Payroll's 804-type wages payable account. Source: [Xero Central: Locked and system accounts](https://central.xero.com/s/article/Locked-and-system-accounts-in-your-chart-of-accounts) (read via the [web-arena-x/webarena-infinity](https://github.com/web-arena-x/webarena-infinity) mirror).
- **CSV import rules** (the current path): up to 300 lines per file, rows with blank date and narration belong to the previous journal, "enter the full tax rate name as it appears in your tax settings", tracking needs both name and option columns, imported journals are drafts, and only advisor / standard+reports roles can import or post. Source: [Xero Central: Add, import and post manual journals](https://central.xero.com/s/article/Add-import-and-post-manual-journals) (same mirror). Matches the practice's `xero-import-format.md`.
- **Xero Payroll (native):** the switch-to-Xero-Payroll setup asks you to "Select the relevant bank account and account codes for the payroll journals" - fixed-shape journals from a fixed mapping, with no per-employee routing. Source: [Xero Central: Switch to Xero Payroll](https://central.xero.com/s/article/Switch-to-Xero-Payroll) (same mirror).
- **Display gotcha from a working Xero poster:** "Xero's Account Transactions report concatenates a ManualJournal's Narration with EVERY JournalLine's own Description when rendering - a long Narration is effectively repeated once per line ... Keep both fields short: Narration carries the period + pay date ONCE, per-line Descriptions carry only what's unique to that line." Source: [LUCANINA/washroute supabase/functions/payroll-xero-post/index.ts](https://github.com/LUCANINA/washroute/blob/main/supabase/functions/payroll-xero-post/index.ts). Digivolve's `[What] - [Employee] - [Month Year] (Mn)` line descriptions repeat the period on every line; harmless but noisy.

### 6. Xero app connection limits decide the architecture

**Confidence: high** (multiple independent 2025-26 restatements of Xero's limits page)

- "You can connect up to 25 organisations to uncertified apps." Source: [Klavis-AI/klavis docs/knowledge-base/oauth_app/xero.mdx](https://github.com/Klavis-AI/klavis/blob/main/docs/knowledge-base/oauth_app/xero.mdx), citing [developer.xero.com/guides/oauth2/limits/](https://developer.xero.com/guides/oauth2/limits/); independently "uncertified apps 'can only connect to 25 organisations simultaneously' with no limit for certified apps" (last checked 2026-09-17) in [samarth080/composio-app-research](https://github.com/samarth080/composio-app-research).
- Custom connections: "the application authenticates as itself, and each custom connection can access only one organisation" (client-credentials grant, no user consent step). Source: [freakboy3742/pyxero README](https://github.com/freakboy3742/pyxero). *Best-knowledge, medium confidence:* custom connections are a paid per-organisation add-on in Xero, so 260 of them is a real monthly cost and 260 separate setups by an org admin.
- Rate limits: "60 calls per minute per tenant, 5000 calls per day per tenant, 10,000 calls per minute across all tenants", 5 concurrent; headers `X-MinLimit-Remaining`, `X-DayLimit-Remaining`, `X-AppMinLimit-Remaining`. Source: [airbytehq/airbyte docs/integrations/sources/xero.md](https://github.com/airbytehq/airbyte/blob/master/docs/integrations/sources/xero.md). One journal plus one duplicate-check read per employer per month is nowhere near any of these.
- Consequence: a single practice-owned uncertified OAuth app cannot cover 260 client orgs. Options are (a) Xero App Partner certification of the practice's app (removes the cap; a review process with Xero), (b) 260 custom connections, (c) keep the browser-driven CSV import (no cap, no API, but the highest failure surface - Chrome session, org switching, file chooser), or (d) a hybrid: API for the orgs that fit under 25 (or under certification) and CSV import for the rest. This is the first decision to make.

### 7. Common design decisions across products (the benchmark, distilled)

**Confidence: high** where drawn from findings 2-5; **medium** for BrightPay UI specifics

| Decision | BrightPay (observed) | Staffology (spec) | KeyPay (spec) | Practice today |
|---|---|---|---|---|
| Ledger object | ManualJournal | ManualJournal (via provider) | ManualJournal (via JournalService) | CSV import to draft, then Post |
| Status on post | POSTED | posted on finalise (`autoSubmitJournal`) | posted on finalise (`ExportJournals`) | draft (backfill) / POSTED (agent) |
| Date | pay date (2021) / period end, not always month-end (2026 QBO) | pay date (`PaymentDate`) | `DatePaid` | last day of calendar month |
| Mapping unit | per pay item, per employer file | per pay code + department/cost-centre override | per category + location/entity split | per client JSON, per-employee overrides (`gross_by_name`, `net_by_name`) |
| Per-employee lines | yes, 4 per employee, PAYE credited per employee | `mergeMatchingNominals` toggle | `JournalView` Summary/Details | named per employee, ONE PAYE control line |
| EA | separate journal, only if mapped, silently skipped otherwise | opt-in flag, monthly payers only | opt-in flag | explicit Dr PAYE / Cr ER NIC pair, tied to P30 |
| Pensions | per pay item | per scheme pay code with narrative | employer/employee pension liability+expense | per-member pensions payable lines |
| Source marker | narration `Sent from BrightPay` | `link` to journal stored on PayRunJournal | `JournalExternalReferenceId` stored | narration `Payroll - Mon YYYY (Mn)` |
| Duplicate guard | none (re-send = second journal) | status per pay run; `force` to re-post | `FailureAlreadyExported` | "check Posted tab first" (human/agent rule) |
| Re-run handling | void old by hand | re-post with `force`, old not reversed | re-export, old not reversed | flag, never correct earlier months |

Distilled decisions the market has converged on: nominal mapping per pay element with a *group* override dimension (department / location), never per person; pay-date journals; posted, not drafted, when triggered by a finalised run; the ledger id stored back against the run as the proof of posting; EA as an explicit, separately-mapped line; and no automatic reversal on re-run.

### 8. How a peer practice made BrightPay's "native" posting reliable at ~100 employers

**Confidence: high** (their code and design docs are public)

Almond Valley Accounting (Scotland; 603 active clients, 99 payroll employers - 96 QuickBooks, 2 Xero, 1 FreeAgent; Bright Manager for practice management) built a Playwright runner that drives BrightPay's own journal wizard and a Supabase control layer. Their verified-on-live-data rules, all transferable:

- Journals matched to a run by **date range and sum of debits**, not by document number (BrightPay sets none) and not by one-journal-per-month (weekly payrolls, catch-up periods, and the separate EA journal all break that).
- **Duplicate = two journals with the same transaction date and the same total.** Missing = task says posted, no journal in range. Orphan = journal with no task. Amount mismatch beyond £0.02. Uncategorised-account = nominal mapping needs attention. All are *findings for a human*, never auto-reversed: "Nothing here writes to QuickBooks."
- `payroll.task` has `UNIQUE (employer_id, kind, period_start, period_end)` to stop the runner double-posting, and they note the limit: "A database constraint cannot see QuickBooks" - hence the independent ledger-side sweep.
- The state machine goes `posted` -> `verified` only when the ledger check matches, with the ledger journal id as `evidence`; 145 rows sat at `posted` (= "BrightPay's screen showed no error") until that was wired.
- Ltd/Limited name matching: "Strip the suffix from BOTH sides" - it "cost five clients on the first run". Digivolve's backfill skill already learned the same lesson (Brandtek IT Services Ltd vs Limited).
- OAuth hygiene: refresh tokens "roll on use and die after ~100 days unused"; a nightly touch of every connected org is what keeps 128 connections alive. A 36-day outage came from disabling a connection on a transient refresh error.
- Quarterly PAYE payers render a quarter, not a month, on BrightPay's HMRC screen; the driver throws `QuarterlyScheduleError` rather than misread a quarter as a month (the practice's own "quarterly payers" note is the Moneysoft equivalent).

Sources: [athena-portal qbo-journal-recon](https://github.com/almondvalleyaccounting/athena-portal/blob/main/supabase/functions/qbo-journal-recon/index.ts), [qbo-portfolio-sweep-plan.md](https://github.com/almondvalleyaccounting/athena-portal/blob/main/docs/qbo-portfolio-sweep-plan.md), [hmrc-timing-and-cis-rules.md](https://github.com/almondvalleyaccounting/athena-portal/blob/main/docs/hmrc-timing-and-cis-rules.md).

### 9. What bureaux and bookkeepers running Moneysoft say about Xero journals

**Confidence: low** (web silent - AccountingWEB / ICB / AAT forums were unreachable and their content is not on GitHub)

Best-knowledge answer: Moneysoft is popular with small bureaux precisely because it is cheap, desktop, and RTI-solid, and its users accept that the accounts side is manual - typing the Employer's Summary into a journal, keeping an Excel journal template per client, or building the Xero manual-journal CSV by hand. Typical pain points reported are: forgetting the Employment Allowance reversal, PAYE control accounts that never clear because the journal credits gross ER NIC, per-employee versus summary preferences of the reviewing accountant, and journals dated in a locked period. Nothing found contradicts this, but nothing found confirms it either; treat it as hypothesis. The one hard datum is a UK payroll job advert of a bureau running "approximately 100 payroll clients of varying sizes on Moneysoft" ([younessZMZ/hrflow_indeed_crawler](https://github.com/younessZMZ/hrflow_indeed_crawler)) - Digivolve's scale is unusual but not unique.

### 10. Is moving to a product with native Xero posting what the market does?

**Confidence: medium**

- Products with native posting exist at every price point (BrightPay, Staffology, KeyPay/Employment Hero, Xero Payroll) and finding 3-4 show that the "hands-free" version is *finalise-triggered auto-post* (Staffology `autoSubmitJournal` + `enableAutoPilot`; KeyPay `ExportJournalsPreference = Immediate/Scheduled`).
- But finding 8 shows a comparable practice that used a native-posting product still had to build a driver, a run-state database and an independent ledger reconciliation, and still found silent EA omissions, duplicates from an earlier automation era, and an employer with no saved mapping. Native posting removed the parser and the CSV, not the control layer.
- Digivolve-specific costs of switching: 260 employer migrations mid-tax-year (YTD figures, EA already claimed elsewhere - a field KeyPay explicitly models: `EmpAllowanceClaimedInAnotherPayrollProductThisTaxYear`), 260 per-employer OAuth authorisations (BrightPay/Staffology connect per employer, and tokens must be kept alive), per-employer or per-employee subscription pricing versus Moneysoft's flat licence, retraining, and Digivolve *just left* BrightPay partly because of the EA/PAYE-control defect that this research confirms is inherent to its journal shape.
- Xero Payroll specifically: fixed journal mapping per org (no directors-to-DLA routing without a separate pay item), a per-org payroll subscription, and the client owning the payroll subscription - workable for clients already on Xero Payroll plans, unattractive as a bureau platform for 260.
- Staffology is the only benchmark whose *bureau API* would let the practice keep its own control layer (post journal per pay run, read `PayRunJournal.status`, `force` re-post) - if a switch were ever made, it is the one to evaluate.

## Implications for the pipeline design

1. **Resolve the Xero access model before writing the poster.** Three viable paths: (a) apply for Xero App Partner certification for a practice-owned app (removes the 25-org cap; needs a review and a compliant OAuth flow); (b) custom connections per org (one org each, client-credentials, paid); (c) keep CSV import for orgs outside the API cap. A pragmatic sequence: build the API poster now, connect the highest-volume 25 orgs to validate it, and run certification in parallel; CSV import remains the fallback path in the same code with the same journal object.
2. **Keep the journal shape the practice already has - it is better than the benchmarks.** Named per-employee gross / ER NIC / net lines, ONE PAYE control line that equals the P30, EA as an explicit Dr PAYE / Cr ER NIC pair, pensions payable named per member. Do not adopt BrightPay's per-employee PAYE credits or its silent EA behaviour. Keep `--date` month-end as the default but store the pay date in the narration so period matching can be done either way.
3. **Give every journal a deterministic key in the narration** (e.g. `Payroll - Aug 2026 (M5) - <employer key> - MS`), keep it short, and make the duplicate guard a *read before write*: `GET ManualJournals?where=Date>=DateTime(...)&&Date<=DateTime(...)` then filter `Status==POSTED` and narration key. Xero offers no idempotency; this is how the washroute poster (`Narration includes payout.id`) and Almond Valley (`same date + same total`) both do it. Also check the Draft tab, because an earlier CSV import may have left a draft.
4. **Post `POSTED`, not draft, once the run has passed the gate** (`verify_figures.py` = VERIFIED, journal balances, PAYE control equals the P30 "Tax & NIC due"). Every benchmark posts on finalise. Drafts remain the mode for backfills and for any client whose convention is unknown.
5. **Store the `ManualJournalID` back against the run before declaring success, and treat "posted but failed to record" as its own failure class** (KeyPay `FailureRecordingJournalReference`; washroute's "Xero is now ahead of our records. Do NOT retry"). `run_log.csv` / the queue should carry `xero_manual_journal_id`, `posted_at`, `status`.
6. **Add a separate read-only reconciliation sweep** after each batch, modelled on Almond Valley's: for each employer-month compare the ledger's journals in the period against the run log - duplicate (same date + same total), missing, amount mismatch (> £0.02), orphan, unbalanced, uncategorised/unknown account. Findings go to a human list; the sweep never writes.
7. **Mapping model:** keep per-client JSON, but restructure it toward the market's shape - codes per *element* (gross, dividend, ER NIC, ER pension, net, PAYE control, pensions payable, dividend tax) with an *override dimension* for a group of people (directors -> 478/835) rather than only `gross_by_name`. Name overrides stay for genuine one-offs. Pull the org's chart of accounts via the API (`GET Accounts`) at mapping time and refuse to post to a code that does not exist or is a system account (Xero returns a warning and drops the line, which would silently unbalance nothing but re-route money).
8. **Never credit net wages to a Xero Payroll "Wages Payable" system account** and never use AP/AR codes; both are rejected (Central article) and KeyPay even has `FailureCannotUseAccountsPayableAccount` for it.
9. **Re-runs:** do not auto-reverse. On a re-run the pipeline should detect the existing journal, HOLD, and offer a human the choice (void + re-post or a difference journal). This is exactly what every product does implicitly.
10. **Locked periods and `ShowOnCashBasisReports`:** expect `FailureAccountPeriodClosed`-type errors (Xero returns a validation error on a locked date); re-date to the first open day and put the true period in the narration, as the existing skill already prescribes. Set `ShowOnCashBasisReports` explicitly (BrightPay leaves it true).
11. **Token hygiene:** refresh tokens expire when unused; with monthly posting a nightly (or at least weekly) refresh-touch of every connected org is required, and a transient refresh failure must not disable a connection (Almond Valley's 36-day outage).
12. **The Moneysoft side is the real bottleneck, not Xero.** If the office machine confirms a native nominal/accounting export from Payroll Manager (open question 1), switch the parser to it and keep the PDF parser as the cross-check; if not, the PDF parser plus the Year-to-Date reconciliation stays the source of truth.
