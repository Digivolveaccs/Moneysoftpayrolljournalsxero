# Xero Accounting API: Manual Journals endpoint, limits, and authentication for a practice with ~260 client orgs

Research date: 2026-09-26. Method: web search (snippets only; developer.xero.com and central.xero.com pages are blocked by the egress proxy, so they could not be read in full), plus the machine-readable Xero OpenAPI spec (`XeroAPI/Xero-OpenAPI/xero_accounting.yaml`, fetched from raw.githubusercontent.com) and the source of `XeroAPI/xero-mcp-server`. Where a claim comes from the OpenAPI spec it is marked **[spec]**; where it comes only from my prior knowledge of the API it is marked **[knowledge]** with a lower confidence.

## Summary

- **The API can do everything the CSV-import step does today, better**: `PUT /api.xro/2.0/ManualJournals` creates a journal in one call, and it can be created directly as `Status: POSTED` (no draft-then-approve round trip needed). Line sign convention is the same as the CSV (debit positive, credit negative). One journal per call, with `summarizeErrors=false` and an `Idempotency-Key`, gives a clean, retry-safe, per-client success/failure signal.
- **The commercial/licensing picture changed on 2 March 2026 and is the single biggest design risk.** Xero replaced the old "25 tenants per uncertified app" rule with paid tiers: Starter (free) is capped at **5 connections**; Core (~A$35/month, ~£18) at 50; Plus (~A$245, ~£120) at 1,000 and needs certification. **Xero states that bespoke integrations built by an accountant/bookkeeper for their own practice are exempt from the new pricing** ("the platform remains free for internal innovation"). How that exemption is claimed in the developer portal, and whether it lifts the 5/50-connection caps for a 260-org practice, is NOT documented in anything found - it must be confirmed with Xero before the architecture is fixed.
- **Custom Connections (client_credentials, one org each) are not the answer at this scale**: £5/month ex VAT per organisation = ~£1,300/month for 260 orgs, and each one must be bought inside the client's org by an admin/standard user (partners cannot buy them on clients' behalf).
- **Auth code + PKCE is the right flow for a script on a staff Mac**: no client secret, one refresh token per authorising staff user covers every org that user has connected (tenant chosen per request via the `xero-tenant-id` header). Access tokens last 30 min; refresh tokens rotate on every use and die after 60 days unused - so the pipeline must refresh at least monthly and persist the new token atomically. A lost rotation has a 30-minute grace window.
- **Connecting 260 orgs is a one-off manual effort**: the standard consent screen connects one organisation per authorisation; multi-select ("Bulk Connections") is only available to Advanced/Enterprise tier apps that have passed a security assessment. Budget ~260 consent flows (~30 s each) by an Administrator/Standard user with the "edit connected apps" permission on each client org (practice staff with adviser access qualify).
- **Rate limits are a non-issue for this workload**: 60 calls/min and 5,000/day per tenant (1,000/day on Starter), 10,000/min app-wide, 5 concurrent. Posting one payroll journal needs ~4-6 calls per org per month.
- **The official Xero MCP server is not viable for the posting step**: it authenticates with a single custom connection (client_credentials) or a static bearer token, always uses the *first* tenant returned by `/connections`, has no token refresh, no `where` filter on manual journals and no tracking support. A ~150-line Python client is simpler and fully controllable.
- **CSV import behaviour is confirmed**: journals import as drafts, rows are grouped into journals by identical narration+date, max 300 lines per file, headers must not be altered. The API path removes the Chrome-driving step and the "drafts need approving" step entirely.

## Findings

### A. ManualJournals endpoint

1. **Confidence: high** - Endpoints and verbs. `GET /api.xro/2.0/ManualJournals` (list, paged), `PUT /ManualJournals` (`createManualJournals` - "Creates one or more manual journals"), `POST /ManualJournals` (`updateOrCreateManualJournals` - "Updates or creates a single manual journal"), `GET/POST /ManualJournals/{ManualJournalID}` (`updateManualJournal` - "Updates a specific manual journal"). PUT = create only; POST = create-or-update (update when `ManualJournalID` is supplied). Sources: [spec], [Manual Journals docs](https://developer.xero.com/documentation/api/accounting/manualjournals), [Requests and responses](https://developer.xero.com/documentation/api/accounting/requests-and-responses).

2. **Confidence: high** - Request/response fields **[spec]**. `ManualJournal`: `Narration` (string, the only *required* element), `JournalLines[]`, `Date` (YYYY-MM-DD; "Date journal was posted"), `LineAmountTypes` (`Exclusive` | `Inclusive` | `NoTax`; spec says exclusive of tax by default if omitted - send `NoTax` explicitly for wages journals), `Status` (`DRAFT` | `POSTED` | `DELETED` | `VOIDED` | `ARCHIVED`), `Url` ("shown as 'Go to [appName]' in the Xero app"), `ShowOnCashBasisReports` (boolean, **default true if not specified** - note the CSV import defaults this *off*, so the API and CSV paths differ here), read-only `HasAttachments`, `UpdatedDateUTC` (`/Date(ms)/`), `ManualJournalID` (uuid), `StatusAttributeString` (e.g. `ERROR` when `summarizeErrors=false`), `Warnings[]`, `ValidationErrors[]` (each `{Message}`), `Attachments[]`. `ManualJournalLine`: `LineAmount` ("Debits are positive, credits are negative value"), `AccountCode` or `AccountID`, `Description`, `TaxType` ("The tax type from TaxRates"), `Tracking[]` ("Any JournalLine can have a maximum of 2 TrackingCategory elements"), read-only `TaxAmount`, `IsBlank`. Source: [Xero-OpenAPI xero_accounting.yaml](https://raw.githubusercontent.com/XeroAPI/Xero-OpenAPI/master/xero_accounting.yaml).

3. **Confidence: high** - A journal can be created directly as POSTED. Xero's accounting release notes state "You can now enter 'POSTED' Manual Journals in addition to 'DRAFT'"; the MCP server's create handler passes `status` straight through to `createManualJournals` and documents "draft by default". Source: [Accounting API release notes](https://developer.xero.com/documentation/api/accounting/releasenotes), [create handler source](https://raw.githubusercontent.com/XeroAPI/xero-mcp-server/main/src/handlers/create-xero-manual-journal.handler.ts).

4. **Confidence: medium** - Draft → posted is `POST /ManualJournals/{id}` with `Status: POSTED`. The spec exposes `updateManualJournal` with the full object; the MCP `update-manual-journal` handler resends narration, lines, date and status together. Whether omitting `JournalLines` on the update preserves existing lines is not documented in anything found **[knowledge: for invoices, Xero replaces line items with whatever you send; assume the same and always resend the full journal]**. Voiding a posted journal = POST with `Status: VOIDED`; deleting a draft = `Status: DELETED` **[knowledge]**. Source: [spec], [update handler](https://raw.githubusercontent.com/XeroAPI/xero-mcp-server/main/src/handlers/update-xero-manual-journal.handler.ts).

5. **Confidence: high** - `summarizeErrors` and validation structure. Query param `summarizeErrors` - "If false return 200 OK and mix of successfully created objects and any with validation errors" **[spec]**; with the default (true) a validation failure returns HTTP 400 with `ErrorNumber: 10, Type: ValidationException`, `Elements[]` each carrying `ValidationErrors[].Message`. Source: [Requests and responses](https://developer.xero.com/documentation/api/accounting/requests-and-responses), [Response codes](https://developer.xero.com/documentation/api/accounting/responsecodes).

6. **Confidence: medium** - Batching semantics: a community developer reported that when PUTting an array of 10 manual journals, one failing validation, "the 9 other journals may still be POSTED within Xero while the API returns the error". Implication: **never batch multiple clients' journals in one call**; one journal per request so success/failure is unambiguous. Source: [Xero community: Batch/Multiple Manual Journals](https://community.xero.com/developer/discussion/100616205). Generic guidance that PUT/POST accept arrays of up to 50 items: [Coefficient](https://coefficient.io/xero-api/xero-api-rate-limits).

7. **Confidence: high** - Lock-date error text (from many integrators' help pages): `The document date cannot be before the period lock date, currently set at DD/MM/YYYY` and the sibling `The document date cannot be before the end of year lock date, currently set at DD/MM/YYYY`. Fix is Accounting > Advanced > Financial settings in the org (or date the journal on the first open day). Sources: [Datamolino](https://helpdesk.datamolino.com/en/articles/1518926-the-document-date-cannot-be-before-the-period-lock-date-currently-set-at-day-month-year), [Dext](https://help.dext.com/en/articles/105721-the-document-date-cannot-be-before-the-end-of-year-lock-date-currently-set-at-date), [Pleo](https://help.pleo.io/en/articles/6018863-explained-exporting-errors-with-xero), [ApprovalMax on lock dates and manual journals](https://support.approvalmax.com/portal/en/kb/articles/how-is-a-lock-date-handled-for-xero-manual-journals).

8. **Confidence: medium** - Invalid/archived account error text: `Account code 'XXX' is not a valid code for this document` is documented for credit notes and invoices, and integrators attribute it to archived/non-existent accounts; the same validator is believed to apply to manual journals **[knowledge]**. Unbalanced journal: the UI wording is "Transaction must balance"/"total debits must equal total credits"; the exact API message string was not found (low confidence on wording; the *behaviour* - rejection - is certain). System accounts (Accounts Receivable, Accounts Payable, bank accounts, and the CIS system accounts) cannot be journaled to at all; Xero's official workaround is a secondary non-system account. Sources: [Lightspeed](https://x-series-support.lightspeedhq.com/hc/en-us/articles/25533984397467-Xero-Error-Account-code-is-not-a-valid-code-for-this-document), [Xero-NetStandard #364](https://github.com/XeroAPI/Xero-NetStandard/issues/364), [Xero Central: Locked and system accounts](https://central.xero.com/0/article/Locked-and-system-accounts-in-your-chart-of-accounts), [Xero product ideas: journals to AR/AP](https://productideas.xero.com/forums/967136-banking-chart-of-accounts/suggestions/47565272-allow-journals-to-accounts-payable-receivable), [Webgility](https://www.webgility.com/blog/xero-journal-entry-errors).

9. **Confidence: high** - `Idempotency-Key` is supported on `PUT`/`POST ManualJournals` **[spec: `idempotencyKey` header param is listed on the ManualJournals PUT/POST operations]**: "This allows you to safely retry requests without the risk of duplicate processing. 128 character max." Xero's guide says it applies to all POST/PUT/PATCH across all APIs, header is case-insensitive, and recommends four concatenated UUIDs or any unique key derived from your own object IDs. **Not found: how long Xero remembers a key** **[knowledge: 24 hours; confidence low]** - so idempotency protects retries within a run, not re-runs a week later; duplicate detection across runs must be your own ledger (finding 10). Sources: [Idempotent requests guide](https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/), [spec].

10. **Confidence: medium** - GET filtering for duplicate detection **[spec]**: `GET /ManualJournals` supports `If-Modified-Since`, `where` ("Filter by an any element", example `Status=="DRAFT"`), `order` (e.g. `Date ASC`), `page` (100 journals per page, with lines) and `pageSize`. Xero's efficiency guidance: keep `where` to simple `==`/`AND` on optimised fields (Status, Date), avoid long clauses (timeouts). A Narration equality filter is *syntactically* allowed by "any element" but is not an optimised filter; the safer pattern is `where=Date>=DateTime(2026,08,01) AND Date<=DateTime(2026,08,31) AND Status=="POSTED"` then match narration/amount client-side. Note this is the *ManualJournals* endpoint; the separate *Journals* (general ledger) endpoint has no `where` and needs the `accounting.journals.read` scope, which since March 2026 is gated behind the Advanced tier/security assessment - avoid it. Sources: [spec], [Efficient data retrieval](https://developer.xero.com/documentation/api/efficient-data-retrieval), [Requests and responses](https://developer.xero.com/documentation/api/accounting/requests-and-responses), [Journals endpoint](https://developer.xero.com/documentation/api/accounting/journals).

11. **Confidence: low** - Field length / line-count limits. The OpenAPI schema declares **no `maxLength` on `Narration` or line `Description` and no maximum number of `JournalLines`**; the only documented line cap is the 300-line CSV import limit (finding 24). **[knowledge: Xero text fields on transactions are generally 4,000 chars; the UI has accepted journals of several hundred lines.]** Payroll journals here are at most a few dozen lines, so this is not a practical constraint, but keep narrations short (< 100 chars) for the UI list view. Source: [spec] (absence of limits), [Xero Central 300-line import limit](https://central.xero.com/0/article/Add-import-and-post-manual-journals-AU).

### B. Organisation, Accounts, TaxRates (for pre-flight validation)

12. **Confidence: high** - `GET /Organisation` returns `PeriodLockDate` and `EndOfYearLockDate` ("Shown if set" - i.e. absent when no lock is set), in `/Date(ms+0000)/` format **[spec]**. Read once per run per org and refuse to post any journal dated on/before the later of the two. Sources: [spec], [Organisation endpoint](https://developer.xero.com/documentation/api/accounting/organisation).

13. **Confidence: high** - `GET /Accounts` (scope `accounting.settings.read`) returns per account: `Code` (alphanumeric, max 10 - so `821-25-26` style codes fit), `Name` (max 150), `Type`, `Status` (`ACTIVE` | `ARCHIVED` | `DELETED`), read-only `Class` (`ASSET|EQUITY|EXPENSE|LIABILITY|REVENUE`), read-only `SystemAccount` (enum includes `DEBTORS`, `CREDITORS`, `GST`, `WAGEPAYABLES`, `CISLIABILITY`, `CISLABOUR`, `CISASSET`... or ""/null for normal accounts), `EnablePaymentsToAccount`, `ShowInExpenseClaims`, `TaxType` (default tax rate), `ReportingCode`. Use `?where=Status=="ACTIVE"` and reject any mapping code that is missing, `ARCHIVED`, or has a `SystemAccount` value other than empty (with the caveat that Xero *does* allow journals to some system accounts, e.g. `WAGEPAYABLES`/Retained Earnings - only AR/AP/bank/VAT are hard-blocked; treat any SystemAccount as "needs a human once", then whitelist). Sources: [spec], [Accounts endpoint](https://developer.xero.com/documentation/api/accounting/accounts).

14. **Confidence: medium-high** - Tax type for "No VAT". The `TaxType` enum in the spec includes `NONE`; Xero Central describes "No VAT (0%)" as a system-defined UK rate that cannot be edited; a UK developer confirms `NONE` works for UK organisations. Recommended: on first contact with each org, `GET /TaxRates` and assert a rate with `TaxType == "NONE"` exists (its display name should be "No VAT"), then send `TaxType: "NONE"` on every line with `LineAmountTypes: "NoTax"`. Sources: [spec], [Tax rates endpoint](https://developer.xero.com/documentation/api/accounting/taxrates), [Xero Central: Default tax rates UK](https://central.xero.com/0/article/Default-tax-rates-UK), [n8n community thread](https://community.n8n.io/t/xero-node-doesn-t-accept-valid-uk-taxtype-output2-vat-on-income/220604).

### C. Rate limits

15. **Confidence: high** - Per tenant: 60 calls/minute and 5,000 calls/day (Core tier and above; **Starter tier apps get 1,000/day per org**); app-wide 10,000 calls/minute across all tenants; 5 concurrent calls in progress. Response headers `X-DayLimit-Remaining`, `X-MinLimit-Remaining`, `X-AppMinLimit-Remaining` on every call; on breach HTTP 429 with `X-Rate-Limit-Problem` (which limit) and `Retry-After` (seconds). Recommended handling: honour `Retry-After` exactly, otherwise exponential backoff with jitter; run orgs sequentially (concurrency 1) - the workload is ~5 calls per org per month so no limit will ever be approached. Sources: [OAuth 2.0 API limits](https://developer.xero.com/documentation/guides/oauth2/limits/), [Rate limits best practice](https://developer.xero.com/documentation/best-practices/integration-health/rate-limits/), [Limits FAQ](https://developer.xero.com/faq/limits).

### D. Authentication and multi-org connections

16. **Confidence: high** - Auth code flow with PKCE. Creating an app with the "Auth Code with PKCE" grant type gives a client ID and **no client secret**; native (desktop) apps "are required to use PKCE if connecting directly to the API"; token exchange needs only `client_id` + `code_verifier`. Access tokens expire after 30 minutes. Refresh tokens: "unused refresh tokens expire after 60 days"; **every refresh returns a new refresh token and invalidates the old one**; "if, for whatever reason, you don't receive the response you can retry refreshing your existing refresh token for a grace period of 30 minutes". Xero recommends storing `access_token_expires_at`/`refresh_token_expires_at` alongside the tokens and keeping them in the OS keychain. `offline_access` scope is required to receive a refresh token. Sources: [PKCE flow](https://developer.xero.com/documentation/guides/oauth2/pkce-flow), [Auth code flow](https://developer.xero.com/documentation/guides/oauth2/auth-flow/), [Token types](https://developer.xero.com/documentation/guides/oauth2/token-types), [Managing tokens](https://developer.xero.com/documentation/best-practices/data-integrity/managing-tokens), [OAuth2 FAQ](https://developer.xero.com/faq/oauth2).

17. **Confidence: high** - Scopes. Xero split the broad `accounting.transactions` scope into granular ones; manual journals are covered by **`accounting.manualjournals`** (write) and `accounting.manualjournals.read`; chart of accounts / organisation / tax rates need `accounting.settings.read`; `offline_access` for refresh tokens; `openid profile email` optional for identifying the authorising user. Existing broad scopes keep working until September 2027 for apps that already have them, but the MCP server notes granular scopes are "required for new apps". `accounting.journals.read` (GL Journals endpoint) is no longer granted by default and, from March 2026, needs the Advanced tier plus a security assessment - it is not needed for this pipeline. Sources: [Scopes](https://developer.xero.com/documentation/guides/oauth2/scopes/), [Xero devblog: scope changes](https://devblog.xero.com/upcoming-changes-to-xero-accounting-api-scopes-705c5a9621a0), [Apideck summary](https://www.apideck.com/blog/xero-scopes), [Databuzz](https://support.databuzz.com.au/article/741-changes-to-xero-accounting-api-scopes), [MCP client source](https://raw.githubusercontent.com/XeroAPI/xero-mcp-server/main/src/clients/xero-client.ts).

18. **Confidence: high** - Connections endpoint. `GET https://api.xero.com/connections` (bearer token, no tenant header) returns `[{id, authEventId, tenantId, tenantType, tenantName, createdDateUtc, updatedDateUtc}]` for every org the token's user has connected to the app; `?authEventId=` narrows to the orgs authorised in one consent flow; `DELETE /connections/{id}` (the connection id, not tenantId) returns 204 and removes that org without invalidating the token. Every accounting call then carries `xero-tenant-id: <tenantId>`. One user's token therefore serves all of that user's connected client orgs. Sources: [Xero tenants](https://developer.xero.com/documentation/guides/oauth2/tenants/), [Managing connections](https://developer.xero.com/documentation/best-practices/managing-connections/connections/), [devblog: disconnect via portal](https://devblog.xero.com/new-disconnect-xero-tenants-via-the-xero-developer-portal-7d61600c7fad).

19. **Confidence: high** - Consent screen and multi-org selection. In the standard flow the user picks **one organisation** from a dropdown of orgs they can access (the list is determined by the scopes requested); "Bulk Connections" adds a multi-select with Select/Deselect-all and search, no cap on how many orgs per flow - but "partners are required to take a security assessment and be part of the Advanced or Enterprise tier before they can use Bulk Connections in production". So for a practice app on Starter/Core (or under the practice exemption) expect one consent flow per client org. Sources: [App partner features - Bulk Connections](https://developer.xero.com/documentation/xero-app-store/app-partner-guides/app-partner-features/), [Pricing and policy FAQ](https://developer.xero.com/faq/pricing-and-policy-updates), [Multi-tenancy](https://developer.xero.com/documentation/best-practices/managing-connections/multi-tenancy/).

20. **Confidence: medium-high** - Who can authorise. Xero Central: "You must be a standard or administrator user with the edit connected apps permission to connect apps to your organisation or practice" (Xero renamed the Adviser role to **Administrator**; existing access unchanged). Practice staff who hold Administrator/Standard access to a client org through Xero HQ / the partner plan can therefore authorise from their own login; the consent dropdown lists every org that login can access. Viewer/read-only, cashbook-client and managed-user roles cannot. Sources: [Xero Central: Connect an app](https://central.xero.com/0/article/Getting-started-with-Xero-Connected-Apps), [Administrator role](https://central.xero.com/0/article/Adviser-user-role), [Partner plan client user roles](https://central.xero.com/s/article/Client-user-roles), [Permissions FAQ](https://developer.xero.com/faq/permissions), [Cutcher & Neale on the role rename](https://www.cutcher.com.au/insights-and-news/xero-user-permissions-have-changed-what-business-owners-need-to-know).

21. **Confidence: high** - Pricing tiers effective 2 March 2026 (this supersedes the old "25 tenants / uncertified" model). Five tiers based on connected organisations and data egress: **Starter - free, 5 connections, 1,000 calls/day/org, unlimited data**; **Core - A$35/month (~US$22, ~£18), 50 connections, 10 GB egress**; **Plus - A$245/month (~US$155, ~£120), 1,000 connections, 50 GB**; **Advanced - A$1,445/month (~US$895, ~£720), 10,000 connections, 250 GB**; Enterprise - negotiated, unlimited. "In order to add a 6th connection, you will need to first add your payment details. Once that is complete, you will move to the Core tier." Certification is required from Plus upward; App Store listing is possible from Plus; the security assessment (and Journals endpoint, XPM API, Bulk Connections) from Advanced. The 15% App Store revenue share was retired. Xero bills in AUD; GBP figures are conversions, not list prices. Sources: [Pricing](https://developer.xero.com/pricing), [Pricing and policy FAQ](https://developer.xero.com/faq/pricing-and-policy-updates), [Accounting Today](https://www.accountingtoday.com/news/xero-shifts-to-tiered-pricing-model-for-developers), [Truto](https://truto.one/blog/xero-api-pricing-changes-2026-costs-tiers-and-how-to-minimize-egress/), [Maesn](https://www.maesn.com/blog/xero-partnership-guide/), [Codat](https://docs.codat.io/updates/260116-xero-pricing/), [Databuzz](https://www.databuzz.com.au/changes-to-the-xero-developer-pricing/).

22. **Confidence: medium** - **Practice exemption.** Xero's own FAQ states: "Bespoke integrations for accountants and bookkeepers built for your own practice or a single client are exempt from new pricing policies", "the platform remains free for internal innovation, whether you're automating workflows or building a bespoke integration for your practice", and "accountants and bookkeepers can still access the Journals endpoint and XPM API for free by completing the security assessment". Also exempt: Custom Connections (unchanged terms), financial-services apps, conversion apps, franchise apps. **What was NOT found anywhere**: the mechanism (a checkbox/app category in the developer portal? an application to Xero?), whether the exemption removes the 5- and 50-connection caps or merely the fees, and whether it removes the certification requirement above 50 connections. Digivolve has ~260 payroll clients, so this is the crux. Sources: [Pricing and policy FAQ](https://developer.xero.com/faq/pricing-and-policy-updates), [Xero Central: How Xero Developer changes affect your practice](https://central.xero.com/0/article/How-Xero-Developer-changes-affect-your-practice-AU), [Accounting Today](https://www.accountingtoday.com/news/xero-shifts-to-tiered-pricing-model-for-developers).

23. **Confidence: medium** - Legacy uncertified limits still published. The "Managing connections" and "OAuth 2.0 limits" pages still say uncertified apps are limited to 25 tenant connections and each organisation may connect at most 2 uncertified apps (error: "You can only connect two uncertified apps to an organisation"). It is unclear whether these survive the tier model or were folded into it (the tier caps of 5/50 are stricter anyway). The 2-per-org rule matters: if a client already has two uncertified apps connected (e.g. a bespoke tool from another provider), the practice app cannot connect until one is removed or the app is certified. Sources: [Managing connections](https://developer.xero.com/documentation/best-practices/managing-connections/connections/), [OAuth 2.0 API limits](https://developer.xero.com/documentation/guides/oauth2/limits/), [Xero Central Q: Uncertified app connection limit](https://central.xero.com/s/question/0D53m00008vmH1FCAU/uncertified-app-connection-limit), [Xero product idea on the 2-app limit](https://xero.uservoice.com/forums/5528-accounting-api/suggestions/46812589-increase-the-number-of-uncertified-apps-you-can-li).

24. **Confidence: high** - Custom Connections. Premium option using the `client_credentials` grant, **one Xero organisation per connection**, available in UK/AU/NZ/US, priced **£5/month ex VAT per connection** (A$10, NZ$10, US$5), billed to the subscriber; must be bought by an administrator/standard user of that org (or a practice user with the "connect third-party add-ons" permission), and "Partners with access to their clients' organisations can't purchase apps or custom connections on behalf of their clients". Terms unchanged by the 2026 pricing. For 260 orgs that is ~£1,300/month and 260 client-side purchases - not viable; useful only for a handful of orgs (e.g. a test org). Sources: [Custom Connections guide](https://developer.xero.com/documentation/guides/oauth2/custom-connections/), [Xero Central: Create custom integrations](https://central.xero.com/0/article/Create-custom-integrations-and-apps-with-Xero), [Xero devblog: Introducing Custom Connections](https://devblog.xero.com/introducing-custom-connections-72c32297382), [Client Diary pricing note](https://clientdiary.com/knowledgebase/xero-integration-pricing/).

25. **Confidence: medium** - App Partner certification (only relevant if the exemption does not cover 260 connections). Joining is free (no listing fee; the revenue share was abolished), but the review requires at least 3 active customer connections within a 30-day window, meeting Xero's certification checkpoints (security, support docs, terms/privacy, error handling, disconnect handling), and repeats annually; third parties report it takes "several months". Certification exists for App Store apps - nothing found says a private practice tool can or cannot be certified; the practice exemption route is clearly what Xero intends for internal tools. ### E. Official Xero MCP server

## Implications for the pipeline design

1. **Replace "build CSV → drive Chrome → import → post" with one API call per client**: `PUT /ManualJournals?summarizeErrors=false` with `Idempotency-Key = sha256(client_key + tax_period + journal_hash)`, body `{Narration, Date, Status:"POSTED", LineAmountTypes:"NoTax", ShowOnCashBasisReports:true, Url:<link to filed PDF in Dropbox/SharePoint>, JournalLines:[{LineAmount, AccountCode, Description, TaxType:"NONE"}]}`. Keep the CSV generator as the fallback path and as the human-readable audit copy. Decide explicitly whether to post as `POSTED` (hands-free) or `DRAFT` (current "human approves" rule) - the API supports both; a per-client flag in the registry lets the practice graduate clients from DRAFT to POSTED as confidence grows.
2. **Pre-flight per org, every run (3 GETs, cached daily)**: `Organisation` (lock dates → refuse/hold if journal date ≤ lock date; never auto-move the date silently), `Accounts?where=Status=="ACTIVE"` (every mapping code exists, is ACTIVE, is not a hard-blocked SystemAccount), `TaxRates` (a `NONE` rate exists). These three checks eliminate the three most common API validation failures before the write.
3. **Duplicate guard = local ledger first, Xero second**: persist `{tenantId, period, ManualJournalID, UpdatedDateUTC, idempotency_key}` on success; before posting, check the ledger, then `GET /ManualJournals?where=Date>=DateTime(y,m,1) AND Date<=DateTime(y,m,dd) AND Status=="POSTED"` (falls back to Status DRAFT too) and compare narration + total debits client-side; any existing wages-looking journal in the period → HOLD, not post (this preserves the existing skill rule about repeating journals and manually posted clients).
4. **One journal per API call, never arrays**, because partial success within a batch is real and makes reconciliation ambiguous.
5. **Auth**: register one "Mobile or desktop" (PKCE) app for the practice; scopes `openid profile email offline_access accounting.manualjournals accounting.manualjournals.read accounting.settings.read`; redirect `http://localhost:<port>/callback`; token store in the macOS keychain (or an encrypted file in the profile folder, never Dropbox); atomic write of the new refresh token before using the new access token; a scheduled "keep-alive" refresh at least every 14 days independent of payroll runs; alerting when `refresh_token_expires_at` < 7 days or a refresh returns `invalid_grant` (→ re-consent required). One authorising staff login (Matt's or a dedicated practice-admin login with adviser access to all client orgs) means one token for all tenants; a second staff login can be a hot spare.
6. **Onboarding 260 orgs is a manual, one-off, ~3-hour job** (one consent per org unless the exemption unlocks Bulk Connections). Build an `authorise.py` that loops: open consent URL → user picks the next org → callback → `GET /connections?authEventId=` → append tenantId/tenantName to the client registry, matched to the Moneysoft employer key with the same "Ltd vs Limited" fuzzy rules the skills already use. Pause and re-run the loop as new clients arrive.
7. **The licensing question decides the architecture and must be settled before build** (see open questions). Three scenarios: (a) practice exemption lifts connection caps → single PKCE app, £0; (b) exemption only waives fees but caps stay → Starter/Core limits (5/50) force either certification (Plus, months) or multiple apps (each capped; also each org may only hold 2 uncertified apps) - messy; (c) no exemption → Plus tier ~£120/month plus certification. Custom Connections (~£1,300/month, client-side purchases) are ruled out except for a sandbox org.
8. **Rate limits need only trivial handling**: sequential orgs, honour `Retry-After`, cap retries at 3 with jitter, log `X-DayLimit-Remaining`. On Starter (1,000/day/org) the workload is still two orders of magnitude below the cap.
9. **Do not build on the Xero MCP server**; write a small Python module (requests + PKCE + keychain) exposed to the payroll-agent skill as `xero_post_journal.py <client_key> <period>` that prints `POSTED id=<ManualJournalID>` / `HOLD reason=<ValidationErrors[0].Message>` in the same log-line style the skill already parses.
10. **Error taxonomy for the run summary**: lock date (needs Matt: unlock or approve alternate date), invalid/archived code (needs mapping fix), balance (generator bug - should be impossible given the penny-perfect gate), system account (mapping fix), 401 `invalid_grant` (re-consent), 403 on tenant (org disconnected/removed the app → re-consent), 429 (auto-retry), 5xx (retry then queue).
