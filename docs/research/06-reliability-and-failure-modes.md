# Failure-mode catalogue and reliability patterns for the Moneysoft → Xero payroll-journal pipeline

Research date: 2026-09-26. Method: **Part A** is extracted from the practice's own skills (`payroll-agent/SKILL.md`, `references/moneysoft-playbook.md`, `references/validation-and-holds.md`, `references/extraction-rules.md`, `references/setup.md`, `browns-payroll-journal/SKILL.md`, `xero-payroll-backfill/SKILL.md`, `xero-journal-creator/references/xero-import-format.md`) — every row marked *practice-observed* is a thing that actually happened, with the client/date where the skill records it; rows marked *anticipated* are failure modes the skills guard against but have not (yet) been seen. **Part B** relies on the source-backed findings already in `docs/research/01`–`04` (Xero OpenAPI spec, Xero developer guides via snippets, Dropbox help pages, Moneysoft support pages, the KeyPay/Staffology/BrightPay/Almond Valley reference implementations) and on engineering knowledge labelled **[knowledge]**. The web-search budget for this session was exhausted before this topic was reached and WebFetch is egress-blocked (healthchecks.io, developer.xero.com, moneysoft.co.uk all refused), so **no new web source was read for this document**; where a pattern is stated from engineering practice rather than a source, confidence is capped at medium and it says so.

## Summary

- **Seventy-odd distinct failure modes are already known**; roughly half were observed live in Jul–Aug 2026 (wrong Dropbox folder, Brandtek duplicate pay file and repeating journal, Cine Spark's £2,523 overstatement, Crowmotion's false duplicate hold, Catchfire hidden by a missing `staff[]=all`, four missed HMRC popups, a fuzzy BM tick that completed the wrong task). The pipeline is not fighting hypothetical risks; it is fighting a catalogue.
- **The two failure classes that can silently put wrong money in a client ledger are (1) reading the wrong source (stale folder, stale twin `.pay`, report window swept into the PDF) and (2) posting with the wrong mapping (814 = PAYE Payable at Brandtek, DLA routing, chart variation).** Everything else is loud or recoverable. Design effort belongs on source-of-truth selection and mapping provenance, not on retries.
- **Idempotency has to be layered**: Xero's `Idempotency-Key` protects a retry within minutes; the deterministic narration `Payroll - <Mon-YYYY> (Mn)` plus a pre-flight `GET /ManualJournals` by date window protects across runs; the write-ahead ledger row (`posting` → `posted` + `ManualJournalID`) makes a crash between POST and record recoverable by *adopting* the journal Xero already holds. All three are needed; none alone is enough. The `src/msx` code already implements this shape.
- **Reconciliation gates before any write are the practice's proven control** (penny-perfect re-derivation of every employee, Total row, Tax & NIC Due, TOTAL NET OUTLAY, P30 tie, journal balance = 0.00). The gate should also cover *history*: YTD ÷ elapsed months vs the previous journals, and "does this org already carry a wages journal for this month?" — both catch problems the per-month arithmetic cannot.
- **Hands-free means the absence of a run must be an alert.** The current run-report-as-heartbeat convention ("if it stops arriving, something is stuck") depends on a human noticing silence. A dead-man's-switch (ping on every completed run, alert on *no* ping) and a monthly completeness sweep ("every expected client-month has a POSTED journal by the 20th") turn silence into a signal.
- **Staged rollout per client (shadow → draft → post) with objective promotion criteria** is how a 260-org book goes hands-free without a big-bang. The mapping file already carries `mode`; what is missing is the promotion rule (N consecutive clean shadow runs whose figures match a human-posted journal to the penny, then N clean drafts approved unchanged) and the automatic demotion rule (any hold → back one step).
- **Two Macs, one Dropbox folder, one Xero app: the pipeline must be single-writer.** Moneysoft's lock does not cross Dropbox replicas, SQLite on Dropbox corrupts, and a rotated Xero refresh token used from two machines invalidates one of them. Designate one posting machine; the second is a cold spare that runs only after a lease in the state store expires.
- **Secrets: Keychain for the Xero refresh token, atomic write of every rotation, a keep-alive refresh independent of payroll, and an alert when the token is within 7 days of its 60-day death.** A lost rotation has a 30-minute grace window and after that only a human re-consent recovers it — this is the most likely cause of a silent multi-week outage.

## Findings

The fourteen mitigations that matter most, each stated as a claim with its evidence. The full catalogue (Part A) and the pattern detail (Part B) follow.

1. **Confidence: high** — **Reading the wrong source is the dominant silent failure and needs five explicit guards** (pinned folder, duplicate-`.pay` scan, conflicted-copy scan, size-stable check, employer-name-on-PDF assertion). Practice-observed: three Moneysoft folders on one Mac (263 / 34 / 4 files, 03-Aug-2026); Brandtek's stale twin `.pay` with no PAYE ref; a leftover report window produced 4 payslips for a 1-employee client. Dropbox's own rules say conflicted copies arise when a file is "left open on another user's computer". Sources: `payroll-agent/SKILL.md` (practice); [Dropbox: What's a conflicted copy?](https://help.dropbox.com/organize/conflicted-copy); [Dropbox online-only files on macOS](https://help.dropbox.com/sync/online-only-mac); [Moneysoft: Working from home](https://moneysoft.co.uk/support/working-from-home-payroll-manager/).
2. **Confidence: high** — **Per-client mapping must assert the Xero account's name/type, not just that the code exists**, because the same code means different things in different orgs (814 = PAYE Payable at Brandtek; BMBD 7000/7020/2210; Catchfire 478→835 DLA). `GET /Accounts` returns `Code`, `Name`, `Type`, `Status`, `SystemAccount` per account, so the assertion is one cached call per org per run. Sources: `payroll-agent/SKILL.md` (practice); [Xero Accounts endpoint via OpenAPI spec](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml); [Xero Central: Locked and system accounts](https://central.xero.com/s/article/Locked-and-system-accounts-in-your-chart-of-accounts).
3. **Confidence: high** — **Xero offers no external-reference field on ManualJournals; duplicate prevention is the caller's job**, so the deterministic narration `Payroll - <Mon-YYYY> (Mn)` plus a pre-flight `GET /ManualJournals` by date window is the cross-run dedupe. Every benchmark product does the same (Staffology `force=true`, KeyPay `FailureAlreadyExported`, Almond Valley "same date + same total = duplicate"). Sources: [Xero OpenAPI spec](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml); [Xero Manual Journals docs](https://developer.xero.com/documentation/api/accounting/manualjournals); [staffology swagger mirror](https://github.com/SynergiTech/staffology-swagger); [keypay-dotnet-v2](https://github.com/Thinkei/keypay-dotnet-v2); [athena-portal qbo-journal-recon](https://github.com/almondvalleyaccounting/athena-portal/blob/main/supabase/functions/qbo-journal-recon/index.ts).
4. **Confidence: high (support) / low (retention window)** — **`Idempotency-Key` on PUT/POST ManualJournals makes in-run retries safe** ("safely retry requests without the risk of duplicate processing", 128 chars). How long Xero remembers a key is undocumented in anything found (**[knowledge]** ~24 h), so it does not replace finding 3. Sources: [Xero idempotent requests guide](https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/); [OpenAPI spec](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml).
5. **Confidence: high** — **A write-ahead ledger row (`posting` before the call, `posted` + `ManualJournalID` after) plus an "adopt" path on restart is required**, because a crash between POST and record is a real class — KeyPay names it `FailureRecordingJournalReference`. The ledger must be local SQLite (WAL), never on Dropbox. Sources: [keypay-dotnet-v2 JournalExportStatus](https://github.com/Thinkei/keypay-dotnet-v2); `src/msx/state.py`, `src/msx/poster.py` (practice); **[knowledge]** for SQLite-on-sync corruption.
6. **Confidence: high** — **Penny-perfect reconciliation before any write is the proven control**, and it must be extended with history checks: YTD ÷ elapsed months vs posted journals (Cine Spark: £1,047.50/month posted vs £416.66 proven — £2,523 overstated, the figure belonging to another client) and a wages-journal scan of the target month (Brandtek's repeating £2,095 journal exists for future months). Prior-period differences are flagged, never corrected. Sources: `payroll-agent/SKILL.md`, `browns-payroll-journal/SKILL.md`, `xero-payroll-backfill/SKILL.md` (practice).
7. **Confidence: high** — **One journal per API call, `summarizeErrors=false`**: a community report says that when an array of 10 journals is PUT with one invalid, "the 9 other journals may still be POSTED while the API returns the error". Source: [Xero community: Batch/Multiple Manual Journals](https://community.xero.com/developer/discussion/100616205).
8. **Confidence: high** — **Lock dates must be read from `GET /Organisation` (`PeriodLockDate`, `EndOfYearLockDate`) before posting and never auto-moved**; the API error is "The document date cannot be before the period lock date, currently set at DD/MM/YYYY". Sources: [Xero Organisation endpoint](https://developer.xero.com/documentation/api/accounting/organisation); [Datamolino](https://helpdesk.datamolino.com/en/articles/1518926-the-document-date-cannot-be-before-the-period-lock-date-currently-set-at-day-month-year); `browns-payroll-journal/SKILL.md` (practice).
9. **Confidence: high** — **The Xero refresh token is single-use, rotates on every refresh, dies after 60 days unused, with a 30-minute grace window for a lost rotation** — so: Keychain storage, atomic write, a keep-alive refresh every ≤14 days independent of payroll, an alert at 7 days to expiry, and exactly one machine holding the token. Sources: [Xero PKCE flow](https://developer.xero.com/documentation/guides/oauth2/pkce-flow/); [Xero auth flow / token refresh](https://developer.xero.com/documentation/guides/oauth2/auth-flow/); `src/msx/xero_client.py` (practice).
10. **Confidence: high** — **Rate limits (60/min, 5,000/day per tenant; 10,000/min app-wide; 5 concurrent; 429 + `Retry-After` + `X-Rate-Limit-Problem`) are irrelevant at ~5 calls/org/month but need honouring**: sequential orgs, `Retry-After` exact, jittered backoff, max 3 attempts, and a circuit breaker so a Xero outage does not generate 200 holds. Sources: [Xero OAuth 2.0 API limits](https://developer.xero.com/documentation/guides/oauth2/limits/); [Xero rate-limits best practice](https://developer.xero.com/documentation/best-practices/integration-health/rate-limits/).
11. **Confidence: medium** — **A dead-man's-switch (ping on every completed run; alert on *no* ping within period + grace) is the only monitor that turns silence into a signal.** The practice's current convention is "the run report is the heartbeat — if it stops arriving, something is stuck", which relies on a human noticing absence. **[knowledge]**: healthchecks.io-style `/start`, `/`, `/fail` pings; the docs could not be fetched from this environment. Sources: `payroll-agent/references/setup.md` (practice); `src/msx/notify.py`.
12. **Confidence: medium** — **Staged rollout per client (shadow → draft → post) needs objective promotion criteria** (≥2 consecutive clean shadow months matching a human-posted journal to the penny; ≥2 drafts approved unchanged with mapping SHA unchanged) and automatic demotion on any hold or mapping change. The peer practice found that even native BrightPay→ledger posting "was not hands-free at bureau scale" and built an independent ledger-side recon. Sources: [athena-portal qbo-portfolio-sweep-plan](https://github.com/almondvalleyaccounting/athena-portal/blob/main/docs/qbo-portfolio-sweep-plan.md); `payroll-agent/references/validation-and-holds.md` (review mode, practice); **[knowledge]** for the criteria.
13. **Confidence: high** — **Config-as-code for mappings**: git-versioned JSON per client, schema-validated at load, mapping SHA recorded on every ledger row and embedded in the journal, `tenant_id` pinned, `approved_by/on` mandatory before leaving shadow, promotion by human commit only. Evidence: mapping errors are the second silent-wrong-money class (finding 2), and one-off corrections in old journals were nearly copied as standing rules (Browns 33p dividend rounding). Sources: `browns-payroll-journal/SKILL.md`, `clients/_template.json`, `src/msx/mapping.py` (practice).
14. **Confidence: medium** — **Two Macs must not both write**: Moneysoft's in-app lock does not cross Dropbox replicas (vendor: not designed for networked use; support reportedly said "do not use Dropbox to store main files, only backups"), SQLite on Dropbox corrupts, and a rotated Xero token used from two machines invalidates one. Designate one posting machine; the second is shadow-only with an explicit take-over after >24 h of silent heartbeat. Sources: [AccountingWEB: Online File Storage](https://www.accountingweb.co.uk/any-answers/online-file-storage-1); [Moneysoft: Temporarily using on a different computer](https://moneysoft.co.uk/support/temporarily-using-payroll-manager-on-a-different-computer/); [Dropbox file locking](https://help.dropbox.com/organize/file-locking); **[knowledge]** for the lease/take-over design.
15. **Confidence: high** — **Monthly-close completeness** ("every expected client-month is posted, nil, or client-posts-own by the 20th") must be a separate read-only sweep classifying each client-month (posted / nil / draft-unapproved / held / no-source / orphan / mismatch), modelled on Almond Valley's duplicates-missing-mismatch-orphans recon, with the PAYE payment deadline (22nd electronic) as the hard stop. Sources: [athena-portal qbo-journal-recon](https://github.com/almondvalleyaccounting/athena-portal/blob/main/supabase/functions/qbo-journal-recon/index.ts); `payroll-agent/references/extraction-rules.md` (22nd deadline, practice).

## Part A — failure-mode catalogue from the practice's own experience

Stages: **trigger** (deciding a client-month is ready) · **extract** (getting reports out of Moneysoft / Dropbox) · **parse** (PDF → figures) · **map** (figures → nominal codes) · **build** (journal lines) · **post** (Xero write) · **reconcile** (proof before/after) · **record** (state, ledger, BM) · **notify** (email, report, holds).

"Human?" — **No** = pipeline handles it; **Once** = a human fixes config/mapping once and the pipeline is self-healing thereafter; **Yes** = a human must act each time.

## Part B — reliability patterns

Each pattern: what it is, why this pipeline needs it, and how it maps onto the practice's data. Source labels: **[practice]** = already in the skills or `src/msx`; **[doc 0N]** = source-backed in the sibling research; **[knowledge]** = engineering practice, no source read for this document.

### B.1 Idempotent posting — three layers

1. **Deterministic external reference in the journal itself** [practice, doc 04]. Narration `Payroll - <Mon-YYYY> (M<n>)` is unique per client-month and is the only field Xero exposes for matching — the ManualJournal schema has no reference/external-id field beyond `Narration` and `Url` (doc 04, OpenAPI spec). Put the source PDF's Dropbox/SharePoint link in `Url` ("Go to [app]" in Xero) and the mapping SHA + source SHA in the *first line's* description or the narration tail (e.g. `… [msx m:3f2a9c s:81d0e4]`) so a reviewer can tell which config produced it.
2. **Pre-flight GET by date window, then match client-side** [doc 03 finding 10]. `GET /ManualJournals?where=Date>=DateTime(y,m,1) AND Date<=DateTime(y,m,last)` (Status filter optional), then: exact narration → already done (skip or adopt); any other wages-looking narration → HOLD (Brandtek repeating journal); nothing → proceed. Xero advises simple `==`/`AND` filters on optimised fields (Status, Date); a Narration equality filter is allowed but not optimised.
3. **`Idempotency-Key` on the PUT** [doc 03 finding 9]. Supported on PUT/POST ManualJournals, 128 chars max, "safely retry requests without the risk of duplicate processing". Key = `sha256(slug + period + payload_sha)`. Retention window is undocumented **[knowledge: ~24 h, low confidence]** — so it protects the retry loop and the crash-recovery re-post, **not** a re-run next week; that is layer 2's job.

**Write-ahead ledger** [practice: `state.py`]. Row `(slug, period)` set to `posting` with `payload_sha`, `mapping_sha`, `source_sha`, `tenant_id`, `idempotency_key` **before** the call; `posted`/`draft` with `xero_journal_id` **after**. Crash between: next run sees `posting`, runs layer 2; exact narration found → adopt (`note="adopted after interrupted post"`); not found → re-PUT with the stored key. Store the key in the row so the retry is byte-identical.

**Never "update to fix".** A changed payload for a `posted` period is a *new* event: HOLD, human voids in Xero (`Status: VOIDED`), row re-armed. Staffology requires `force=true` to re-post; KeyPay returns `FailureAlreadyExported` (doc 04). Copy that stance.

### B.2 Outbox pattern

**[knowledge, medium]** The transactional outbox decouples "decide to post" from "post": the journal payload is committed to the local store as an outbox row in the same transaction as the decision, and a separate step drains the outbox to Xero, marking each row done with the returned id. Benefits here: (a) the build/reconcile step can run on the machine with Dropbox while the drain step runs only on the machine with the Xero token; (b) a Xero outage does not lose work — rows stay `queued` and the next run drains them; (c) the outbox row *is* the audit copy (the CSV the practice already writes to `out_dir`). The existing `queue.py add xero_post …` in `payroll-agent` is an informal outbox; the `journals` table with status `posting` is the formal one. Rule: the drain is idempotent (B.1) and single-consumer (B.13).

### B.3 Exactly-once vs at-least-once with dedupe

**[knowledge, high]** Exactly-once delivery to a remote system is not achievable in general; what is achievable is *at-least-once delivery plus idempotent consumption*, which is observationally exactly-once. Here the "consumer" is Xero and it is only partly idempotent (Idempotency-Key, short window), so the pipeline supplies the rest: deterministic narration + pre-flight GET + ledger. Consequence for the design: every retry path must be safe to run twice, and every step that has side effects (Xero PUT, BM tick, Missive draft) needs its own dedupe key in the ledger — the BM tick and the email draft are *also* at-least-once actions (N2, REC4).

### B.4 Reconciliation gates and hold queue / dead-letter

**Gates before any write** [practice]: per-employee net re-derives; components sum to the Total row; tax + EE NIC + ER NIC (+SL/AOE) − EA = Tax & NIC Due; EE+ER pension = Total Other Payments; net + tax/NIC + pensions = TOTAL NET OUTLAY; journal balances to 0.00; P30 ties (monthly) or is informational (quarterly); every mapped code exists, is ACTIVE, and its Xero name/type matches the mapping's expectation (M4); journal date > lock dates; tenant name matches. **Gates after the write**: read back the journal by id and compare totals/lines/date/status (R1).

**Hold queue = dead-letter with a precise note** [practice: validation-and-holds.md]. A held item carries, in order: client + period; what was asked; what blocked it with verbatim figures; **exact state left behind** ("built, NOT posted" / "POSTED id … but ledger not updated" / "draft created, not approved"); the next human action as an imperative; and, where a client needs chasing, a ready-to-send draft. Holds are written to `HOLDS.md` in `out_dir` and repeated in the run report until cleared. **[knowledge]** Add a `hold_reason_code` enum (copy KeyPay's taxonomy: `AccountsNotConfigured`, `AccountPeriodClosed`, `NotAuthenticated`, `AlreadyExported`, `CannotUseSystemAccount`, `VendorMessage`, `APIError`, `RecordingJournalReference`, `NoJournalId`, `TenantNotSupplied` — doc 04) so the report can group holds and the promotion logic (B.6) can distinguish config holds from data holds. A hold is cleared only by a new successful run for that row, never by editing the ledger.

### B.5 Dead-man's-switch heartbeat

**[knowledge, medium — healthchecks.io docs could not be fetched]** The pattern: the job pings a per-check URL at start (`/start`), on success (`/`), on failure (`/fail`); the monitor expects a ping every *period* and alerts after *period + grace* with no ping, or immediately on `/fail`. The alert is about the *absence* of a run, which no log or email can express. Recommended: one check for `msx run` (period 30 min, grace 2 h, matching the launchd `StartInterval` 1800), one for the monthly completeness sweep (period 1 day during the 6th–20th), one for the token keep-alive (period 14 days). `notify.heartbeat()` already touches a file and optionally GETs `heartbeat_url`; wire it to ping `/fail` on an exception and `/start` at run begin so a hung run is distinguishable from a never-started one. Route alerts to a channel a human actually watches (Missive + SMS/push), not to the same mailbox the run report goes to. Self-hostable if the practice prefers no third party.

### B.6 Staged rollout modes with automatic promotion

Modes exist in the mapping (`shadow` → `draft` → `post`) [practice]. Add the rules:

| Transition | Promotion criterion (all must hold) | Demotion |
|---|---|---|
| `shadow` → `draft` | ≥ 2 consecutive months built with zero holds, **and** the shadow figures equal the journal a human posted for the same month to the penny (or, where the org has no history, Matt approves the mapping: `approved_by`/`approved_on` set) | any hold |
| `draft` → `post` | ≥ 2 consecutive drafts approved in Xero **without edits** (read back the posted journal and compare to the draft payload SHA) **and** mapping SHA unchanged since first draft | any edited draft, any hold, any mapping change → back to `draft` for 1 month |
| any → `shadow` | mapping file changed in a way that alters codes; org chart change detected (mapped code renamed/archived); client posts own journal (PO1) | — |

**[knowledge]** Promotion is *proposed* by the pipeline in the run report and applied by a human editing the mapping (git commit) — never auto-committed — so the promotion is itself audited. Demotion may be automatic (safety direction).

### B.7 Config-as-code for client mappings

[practice + knowledge] `clients/<slug>.json` in git; JSON Schema validated at load (`mapping.validate`) and in CI; a `mapping_sha` (first 16 hex of the canonical SHA-256) recorded on every ledger row and embedded in the journal (B.1) so any journal can be traced to the exact mapping version; `source` and `approved_by/on` fields mandatory before `mode != shadow`; expected Xero account **name and type** per code (M4); `xero.tenant_id` pinned after first resolution (M6); `client_posts_own_journal`, `paye_frequency`, `journal_date`, `active_from/to`. Reviews of mapping PRs are the human control point for the whole book. Never let the run mutate a mapping file.

### B.8 Secrets on a staff Mac

[doc 03 findings 16, practice `xero_client.py`] PKCE public client → no client secret to protect; the refresh token is the crown jewel. Rules: **Keychain** (`KeychainTokenStore`) over a file — survives `~/.config` copies, is per-user, and is not synced by Dropbox/iCloud (verify `~/.config/msx` is *not* inside any synced folder); if a file store is used, 0600 + atomic `os.replace`; store `refresh_token_expires_at` alongside and alert at < 7 days; keep-alive refresh every ≤ 14 days from launchd independent of payroll activity; **exactly one machine holds the live token** — a rotated token used from two machines invalidates one (rotation = single use); backup of the rotating token is *not* meaningful beyond the 30-minute grace, so the recovery plan is "re-consent" (one browser flow, documented in `msx auth login`) and a hot-spare *second authorising login* (another staff member with adviser access) rather than a token copy. Missive token: same file rules, separate item. **[knowledge]** Never log token values; redact `Authorization` headers in the debug log.

### B.9 Retries, jittered backoff, circuit breaker

[doc 03 finding 15 + knowledge] Honour `Retry-After` exactly on 429; on 5xx/timeouts exponential backoff with full jitter (base 2 s, cap 60 s, max 3 attempts); never retry 4xx validation errors (they are holds); 401 → one forced token refresh then fail. **Circuit breaker**: after 3 consecutive transport failures across *different* clients, open the circuit for the rest of the run (mark remaining clients `pending`, not `held`) and ping `/fail` — a Xero outage should not generate 200 hold notes. Concurrency 1; sequential orgs. Log `X-DayLimit-Remaining` per call.

### B.10 Time-zone and date pitfalls

- **UK tax month** runs 6th → 5th; `M<n>` = months since 6 April; PAYE electronic payment due the **22nd** of the following month (19th by post) [practice: extraction-rules.md]. The completeness deadline of "the 20th" sits just inside that.
- **Journal date**: practice convention = last day of the payroll's *calendar* month (matches how BrightPay journals were posted for Browns); benchmarks use the *pay date* (BrightPay, Staffology, KeyPay — doc 04). Keep it a per-client rule; never mix within an org (the YTD check would drift).
- **Xero dates** are `YYYY-MM-DD` on write and `/Date(ms+0000)/` UTC on read [doc 03 finding 2/12]; compare on the date part only; build the `where` window in local date terms. A 31-Mar journal vs a 1-Apr lock date is the classic year-end trap (PO6).
- **[knowledge]** File mtimes are UTC on disk; `settle_seconds` comparisons must use `time.time()` not local wall clock; BST/GMT changeover nights (last Sunday of March/October) can make "mtime 30 s ago" look like an hour either way in naive local arithmetic — use epoch seconds everywhere. launchd `StartInterval` is wall-clock-agnostic; `StartCalendarInterval` is local time.
- Period naming: the report's `Jul-2026` is the *pay month*; do not derive the period from the PDF's mtime (a late-run July payroll filed on 3 Aug is still M4).

### B.11 Dropbox sync hazards

[doc 02 finding 10 + practice `sources.py`] Conflicted copies arise when two users change the same file, when one edits offline, or when "a file is left open on another user's computer" (Dropbox's own rules); files may be online-only placeholders on macOS File Provider; Dropbox writes in place, so a PDF can be readable before it is complete. Rules: parse only after `stable()` (non-empty; size and mtime unchanged over a 1 s sample; mtime ≥ 30 s old); exclude `conflicted copy` / ` (n).pdf` by regex and *raise a hold naming the file* rather than ignoring it; pin the folder "available offline" on the posting Mac; hash the source (`source_sha`) and re-check it immediately before the PUT (a file that changed between build and post is a hold). **[knowledge]** Prefer `os.stat` size+mtime over inotify/FSEvents for Dropbox-synced folders — sync clients emit bursts of events for one logical write.

### B.12 Two machines racing on one client

[knowledge + doc 02] A lease row in the state store (`leases(slug, period, holder_machine, expires_at)`) taken before build and released after record; expiry 15 min; a second machine seeing a live lease skips the client as `pending`. But local SQLite cannot arbitrate across machines, so the lease only works if the state store is shared — which contradicts REC2 (no SQLite on Dropbox). Resolution: **designate one posting machine** (config `machine_name`), have the other machine run in `shadow`-only/read-only unless explicitly promoted (`msx run --take-over` after the primary's heartbeat has been silent > 24 h), and rely on Xero's GET-by-window as the cross-machine arbiter of last resort. For Moneysoft itself: single-writer rule for the Dropbox `.pay` folder (licence + corruption), enforced by team file-locking if the Dropbox plan has it.

### B.13 Monthly-close completeness

[knowledge, modelled on Almond Valley's recon: duplicates, missing, mismatch, orphans, uncategorised — doc 04] A separate read-only job (`msx sweep --period Aug-2026`) run daily from the 6th to the 20th: for every mapping with `active` covering the period, classify the client-month as `posted` (ledger + Xero agree, totals match) / `nil` / `draft-unapproved` / `held` / `no-source` / `orphan` / `mismatch` / `client-posts-own`. Output a one-table report; alert (heartbeat `/fail`) if on the 20th any client-month is not in {posted, nil, client-posts-own}. This is the practice's "every expected client-month has a posted journal by the 20th" control, and it doubles as the monitor for silent failures upstream (no source ≈ payroll not run or PDF not filed).

### B.14 Observability that survives the run

Every run: `run_id`, machine, start/finish, per-client outcome bucket (`posted / draft / shadow / skipped / held / pending / failed`), HTML report by Missive, `HOLDS.md`, heartbeat. Every ledger event appended (never updated) in `events`. Keep the built CSV and the API payload JSON per client-month in `out_dir` as the human-readable audit copy. **[knowledge]** Redact NI numbers from every artefact that leaves the machine (skill hard rail: "no NI in any email").

## Implications for the pipeline design

1. **Source-of-truth selection is a component with its own tests**: pinned folder, duplicate-`.pay` scan, conflicted-copy scan, `stable()` gate, employer-name-on-PDF vs mapping assertion. These five checks cover T1, T2, X1, X3, X7, X8 — the silent-wrong-data class.
2. **Mapping provenance is the second silent class**: per-client JSON in git, schema-validated, with expected Xero account name/type per code, `tenant_id` pinned, SHA on every journal, promotion only by human commit. Add the M4 name/type assertion to `check_accounts` — it is the cheapest defence against the Brandtek-814 problem.
3. **Keep the three-layer idempotency the code already has** (narration + GET window + Idempotency-Key + write-ahead row) and add: stored idempotency key on the row, post-write read-back (R1), and the `client_posts_own_journal` flag so PO1 becomes a permanent skip with a monthly check rather than a monthly hold.
4. **Prefer the API over Chrome for the post step**: PO9, PO10, PO11, REC4-style UI fragility disappear; what remains (PO12 token life, PO13 connection caps) is manageable with keep-alive + alerts, subject to the Xero tier/exemption decision in doc 03.
5. **Make silence impossible**: dead-man's-switch on the run, the sweep and the token keep-alive; completeness sweep to the 20th; `report_always` during rollout.
6. **Holds are the product**: structured reason codes, exact state, next action, and the promotion/demotion logic keyed off them. A hold that recurs monthly for the same reason is a config gap, and the report should say so.
7. **Single posting machine**; second Mac is shadow-only with an explicit take-over command. Do not build a distributed lease on top of Dropbox.
8. **Never auto-correct history**: prior-period differences (Cine Spark), orphan journals, mismatched read-backs are reported, not fixed. Voids are human actions.

## Open questions / things to verify on the office machine

1. **Idempotency-Key retention window at Xero** — test on the demo company: PUT with key K, wait 1 h / 24 h / 48 h, PUT again with K and a changed payload; observe whether a second journal appears. Decides whether crash-recovery may rely on the key beyond the same run.
2. **Exact `ValidationErrors[].Message` strings** for: unbalanced, unknown code, archived code, system account, before lock date, tax type not found — to populate `hold_reason_code`.
3. **Does `.pfi` field 12 advance on pay entry, on FPS, or on file close?** and does the `.pay` mtime change on open/close with no edits? (Decides how noisy the file-system trigger is.)
4. **Does Moneysoft rewrite the Employer's Summary PDF in place or write a temp file and rename?** (Decides whether `settle_seconds=30` is enough or whether Dropbox partial reads are realistic.)
5. **Is the posting Mac's `~/.config/msx` outside every synced folder**, and is the Dropbox Moneysoft folder pinned "available offline" on that Mac only? Is there a Windows-side Dropbox client in the guest (there should not be)?
6. **Dropbox plan: is team file locking available**, and does it block Moneysoft's open on the second Mac?
7. **Which clients post their own wages journal** (Brandtek confirmed; any others?) — needed to seed `client_posts_own_journal` before the first live sweep.
8. **Which quarterly PAYE payers exist** and whether the Employer's Summary monthly Tax & NIC Due is reliable for them (P5/P7).
9. **Employer Totals netting of CIS suffered and statutory recovery** — verify on one client with each (P9).
10. **Xero developer tier / practice-exemption mechanics** (doc 03) — the connection cap is the one thing in this catalogue that could force a different architecture (Custom Connections per org, or a certified app).
11. **Heartbeat provider**: healthchecks.io (hosted or self-hosted) vs a Missive-only convention — confirm the practice will actually watch the alert channel out of hours.
12. **Keychain access from launchd**: confirm the `security` item is readable by the launchd agent without a UI prompt on the posting Mac (a locked keychain after reboot is a plausible silent-failure cause).
